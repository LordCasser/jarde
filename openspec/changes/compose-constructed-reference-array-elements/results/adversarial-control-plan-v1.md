# task 2.2 构造数组组合负控制盘点

## 范围与结论

只读核对 `specs/java8-recovery/spec.md`、`design.md`、`tasks.md`、当前 `crates/jarde-java/src/init.rs`/`build.rs` 测试和 `tests/fixtures/p3-constructed-reference-array-elements-v1`。未改文件，未运行 Cargo、Git、rustfmt 或 Java。下文把“源码/测试里已存在”与“目标测试计划”分开；没有把 OpenSpec 要求或历史审计文字说成通过的测试证据。

task 2.2 的负向组合路径目前仍基本缺测试。已有实现接缝是 `init::verify_array_store` 和 `build::ArrayInitializers::prove_with_composition`，但当前新增的 `composed_reference_array_commits_exact_constructed_values_once` 只验正向 CharSequence/Collection、两种 budget stop 和 cancellation。集成测试 `constructed_reference_array_elements_recover_as_one_complete_same_snapshot_family` 是双 javac 完整 family 正向验收。它们都没有为组合层验证错误 stored ValueId、额外 reader、错误 dup、第二元素结构拒绝的零提交、类型拒绝时正文原子性、旧数组、组合 handler/block/逆序索引或递归里的预算停止。

现有 `init` 测试中若干相近反例只证明其各自旧规则：成员构造器 receiver identity、nested `doubleUse`/跨 block、constructor 参数内 inline array 的 second consumer/handler boundary、嵌套深度上限。它们不能替代“construction 是 fresh initializer 的某个 `aastore` 元素”这一组合断言。完整清单如下。

## 组合测试的最小切分

为避免新 fixture 同时测试层级解析、泛型、平台赋值兼容和构造组合，最小闭环建议分两层：

1. `init.rs` focused proof tests用现有 frozen `Main.class` 完成 stored ValueId反事实、真实 expected store及 wrong `dup` predicate、budget/cancel；必要时在测试内改写临时 class bytes，不覆写 `tests/fixtures`。嵌套构造正例用 `Object[]` + 平台 `StringBuilder` 两层，避免额外类型层级。
2. 将额外 reader、乱序/重复索引、handler split 做少量 classfile-level controls，共享正例的同一简洁方法与类型。对每个变体先断言“已进到哪一层”：实际 array candidate、新 allocation BCI、store pairing、实际 code block 和效果handler；随后再断言拒绝。失败的早期预条件若不是被测边界，测试需调整。
3. 一个 integration negative 负责区分“结构失败”与“类型失败”：前者应在 candidate proof 返回前失败且 `pending_sites`/initializer零提交；后者通过独立 type witness forcing focused builder path，候选结构记录可存在但完整 method/body拒绝，无前半 initializer、独立 new statement、重复 NewRecord或悬空 Java。最终 runtime oracle只用于正例；结构/类型故意拒绝的 control 无需伪装成语义运行成功。

完整正例仍由现有七类同 snapshot 双 javac fixture承担：它已覆盖平台 `CharSequence`/`Collection`/`Throwable`、自有直接/两跳子类与接口，多元素 mark trace 和 fresh initializer。不要把 negative 控制塞进这些方法后再用新语法的早期拒绝作为组合负例。current v1 fixture README说明其源/类/原始oracle冻结；直接改它会破坏该身份，应增版本或在 unit test内生成变体。
