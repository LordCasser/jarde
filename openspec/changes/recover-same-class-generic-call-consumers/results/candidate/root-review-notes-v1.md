## v14 事务定位与未闭合证据

对 VoidDirect，最精确的候选诊断是生成源码中两个成员都标记“same-class generic call dependency did not close over every incoming use”；接受基线和原始/JADX均保留 `sink(T)`、`relay(T)`。输入中只有一个直接 void 调用边 `relay(T) -> sink(T)`，因此这是 generic-call component 的过度回退，不是控制拒绝。当前候选产物没有物理 caller/BCI、expected-vs-observed type 或失败 proof reason 的逐边日志；v14 source snapshot 又只有源文件 hash，故不能从保存证据把“哪个 incoming edge/哪一个证明条件”细化到更具体的内部原因。建议下一步针对 VoidDirect 加一条仅诊断用逐 edge 记录，至少输出 caller PhysicalMethodId、BCI/opcode/descriptor、callee id、最终 caller/callee header proof 结果与触发 rollback 的第一个子条件；不需要猜测是 void result 还是调用实参类型。

SameErasureBinder 与 MultiUseResult 的回退范围不同。前者 baseline 本已将不相容的 method U 擦回 Number，candidate 原样保留该拒绝并保留不相关 class T leaf；后者 baseline 不能完整编译，candidate 只回退由 local alias 多 use 连接的 identity/relay，observer 仍保留 Object 签名。它们的 full reflection 缺口要展示，但不等同于 VoidDirect 的既有 positive regression。是否把这两行的 `required feature` 从默认反射一致改成特定 refusal 判据，需要由 root 按 acceptance 明文决定；本文件不改汇总器，也不替 root 标记最终通过。

## 建议的 root disposition

- `VoidDirect` 保持 GC-01 fail：四腿 baseline 已恢复，candidate 把既有 class-T API 擦除；先查具体 incoming closure 子条件。
- `SameErasureBinder` 与 `MultiUseResult` 保持 `full_reflection_match=false` 的事实；分别按“没把 U 错合并到 T”与“相关 alias/use 组一起安全回退”审阅负控制，不能拿全 API hash 自动判成实现失效，也不能直接抹掉 API 差异。
- GC-08 中 `UnknownIncoming`、`CycleRelay`、`MethodHandleUse`、`MultiUseResult`、`VarargsCall`、`InheritedUnknown` 的 candidate source/marker 与行为证据支持 refusal 或边界 fallback；`CycleRelay`、`MethodHandleUse`、`VarargsCall`、`InheritedUnknown` 的反射还与 accepted baseline 相同。`IncompleteSite` 当前没有真实不完整 site 的证据；先检查冻结输入是否构造正确。
- `BridgeUnknown` full API 与 bridge/runtime behavior 都相等，按正向控制通过。

上述是审阅建议，不修改 candidate-v1 的 exploratory 统计。candidate-v1 同时还受 full record clone 计费缺口限制，不能视为最终验收。
