# 固定 CLI3 的 GC-04/05/08 控制事实

本页为根验收提供逐项证据线索，不作最终架构裁定，也不把拒绝标记或行为 Probe 单独当作拒绝正确的证明。固定输入、四腿 CLI 输出、源码、物理 origin、只读 `javap` 摘录和已保存的 Probe 原始/候选结果都在 [candidate-v3-control-facts.json](candidate-v3-control-facts.json)（SHA-256：`72c270bf5b0c81de5c4c70a8d1ba3f99aeb9dba9300e8fa558db2c21ef82a334`）。其每条记录按样例、JDK 腿（`corretto8` / `openjdk23`）和编译参数腿（`debug` / `nodebug`）定位；每个源码片段带原文件行号，字节码摘录带 `javap` 行号及 BCI。四腿原输入源码逐项一致；无调试信息时 CLI 的局部变量名可能变成 `arg1`、`local2` 等，以下会说明这些输出差异。对原始 input jar 的 `javap` 检查只读；未执行目标类。

七项都是 replay 脚本 `CONTROL_REVIEW_ONLY` 中需要 root 复核的项（脚本 `candidate-acceptance-replay.py` 第 95–102 行）。每项四腿已保存候选编译和 Probe 均退出 0，但这些结果不证明相应调用点排除/拒绝规则。下面“支持范围边界”是供 root 判断的理由，不是通过声明。

- **UnknownIncoming（GC-03/GC-08）**：四腿原源码均为 `identity(T)`、`safe(T) { return identity(x); }`、独立的 `untouched(T)`，以及 `unsafe(Object x) { return identity((T)x); }`；`unsafe` 的 `(T)x` 是源码中的 unchecked cast，擦除后 input javap 显示两个 `invokevirtual identity(Object):Object`（safe 与 unsafe），没有可据以保留该 cast 的运行时 `checkcast`。两处原 receiver 都是省略的 `this`；候选输出改写为 `this.identity(x)` / `this.identity(arg1)`，并将 identity/safe/unsafe 的最终头都留在 Object，同时 `untouched(T)` 仍保留。候选输出在这三个物理方法旁都标记 `same-class generic call dependency did not close over every incoming use`。Probe 行为 `safe+unchecked+independent` 通过，但候选反射不等于原值。边界理由：由 safe 的 `T` 实参不能代表另一条从 `Object` 经 unchecked cast 而来的入边；要拒绝整组同时保留独立 leaf，需依据完整的入边/消费位证明。可定位证据：每腿 JSON 记录；代表输出 [UnknownIncoming.java:13](../candidate/candidate-v3/gc01-08-140/openjdk23/debug/UnknownIncoming/jarde/UnknownIncoming.java:13)，原输入源及 Probe 结果见对应 JSON 记录的 `source_correlation` / `probe`。

- **CycleRelay（GC-08）**：四腿原源码的 `left(T, boolean)` 在条件分支调用 `right(x,false)`，`right(T, boolean)` 对称调用 `left(x,false)`，否则都返回 `x`；两个 receiver 均是隐式 `this`。候选四腿将其发射为 `this.right(x/arg1,false)` 与 `this.left(x/arg1,false)`，两头均为 Object，并带入边闭合拒绝标记。输入 javap 在两方法中保留互为目标的 `invokevirtual right(Object,boolean):Object` / `left(Object,boolean):Object`；Probe 只执行有限分支，行为 `finite-cycle-marker` 通过，反射不匹配。边界理由：循环边不能用彼此尚未证实的类型结论自证；有限运行只说明该次路径终止，不证明推断器正确拒绝了 cycle。可定位证据：[CycleRelay.java:13](../candidate/candidate-v3/gc01-08-140/openjdk23/debug/CycleRelay/jarde/CycleRelay.java:13)，物理 BCI 与四腿输出见 JSON 对应记录。

- **MethodHandleUse（GC-08）**：四腿原源码的 `relay(T x)` 建立 `Function<T,T> f=this::identity`，再执行 `f.apply(x)`；方法引用捕获的 receiver 是 `this`，`apply` 的 receiver 是局部变量 `f`。候选仍发射 `this::identity` 与 `f.apply`（无调试腿局部名为 `local2`），identity/relay 两头为 Object 并各有拒绝标记。input javap 显示 relay 中 `invokedynamic`，BootstrapMethods 使用 `LambdaMetafactory`，目标 `identity(Object):Object` 位于 MethodHandle 常量；实际调用处是 `invokeinterface Function.apply`，不是 caller 内的直接 `invokevirtual identity`。Probe 行为通过，反射不匹配。边界理由：bootstrap 中的 method handle 不能被当作本片直接 invoke 消费位或普通 caller→callee 入边。可定位证据：[MethodHandleUse.java:13](../candidate/candidate-v3/gc01-08-140/openjdk23/debug/MethodHandleUse/jarde/MethodHandleUse.java:13)，bootstrap 与 BCI 摘录在 JSON 对应记录。

- **RawOwnReceiver（GC-05）**：四腿原源码先声明 raw `RawOwnReceiver raw=this`，再返回 `(T)raw.identity(x)`；实际 receiver 是 static type 为 raw 的局部 `raw`，不是参数化的 `RawOwnReceiver<T>`。输入 javap 在 BCI 4 有 `invokevirtual identity(Object):Object`。候选输出把这一处展示为 `this.identity(x/arg1)`，identity/relay 最终头是 Object，二者附有入边闭合拒绝标记；因此输出接收者与原源码静态 receiver 不同，是 root 需要检查的事实。Probe 行为通过、反射不匹配。边界理由：raw receiver 对自己声明的实例泛型方法按 raw 规则选择，不能仅凭同类归属或 erased descriptor 将成员结果替成 class `T`；还需核对实际 AST receiver 类型是否保留，而不能从 marker 推断。可定位证据：[RawOwnReceiver.java:21](../candidate/candidate-v3/gc01-08-140/openjdk23/debug/RawOwnReceiver/jarde/RawOwnReceiver.java:21)，四腿原/候选源码与 physical invoke 见 JSON 对应记录。

- **ReboundOwnReceiver（GC-05）**：四腿原源码将变量静态声明为 `ReboundOwnReceiver<T> receiver=this`；之后经过 `Object alias=receiver`，再把 `(ReboundOwnReceiver)alias`（raw cast 表达式）赋给 `receiver`，最后执行 `(T)receiver.identity(x)`。这个 unchecked assignment 不改变 `receiver` 的声明静态类型；不能据此说原源码最后调用必然按 raw receiver 选择。物理 input 在 BCI 5 有 `checkcast ReboundOwnReceiver`、BCI 11 有 `invokevirtual identity(Object):Object`，字节码自身也不保存该局部变量的泛型静态类型。候选完整源码则将局部实际声明为 raw `ReboundOwnReceiver receiver`（无调试腿对应 `ReboundOwnReceiver local2`），保留 `Object alias` / raw cast 赋值后从这个 raw 局部调用。identity/relay 头均为 Object 并带拒绝标记；Probe 行为通过、反射不匹配。边界理由：Object alias、raw cast 与重绑定路径没有证明可把原 `T` 约束传到调用点；同时候选实际选择的是 raw 局部声明。root 可据此支持保守拒绝边界，但拒绝 marker 本身不证明证明链正确，也不应把候选 raw 局部类型倒推成原源码变量的类型。可定位证据：[ReboundOwnReceiver.java:21](../candidate/candidate-v3/gc01-08-140/openjdk23/debug/ReboundOwnReceiver/jarde/ReboundOwnReceiver.java:21)，原/候选完整局部声明、checkcast/invoke BCI 和四腿差异见 JSON 对应记录。

- **InheritedUnknown（GC-08）**：四腿原源码为 `InheritedUnknown<T> extends ArrayList<T>`，`relay(int index) { return get(index); }`；源码 receiver 隐式为 `this`，候选输出显式为 `this.get(index/arg1)`，返回头仍为 Object。input javap 显示 BCI 2 的 `invokevirtual get(I):Object`；常量池 Methodref 的符号 owner 是 `InheritedUnknown.get`，但类中没有物理 `get` 声明，实际成员来自 `ArrayList<T>`。候选另有 class Signature 投影拒绝标记，Probe 行为通过、反射不匹配。边界理由：符号 owner 写本类并不代表目标是同类已声明方法；泛型父类成员代换属于继承解析，本片声明的同类闭包不能由该 owner 名称推导。可定位证据：[InheritedUnknown.java:4](../candidate/candidate-v3/gc01-08-140/openjdk23/debug/InheritedUnknown/jarde/InheritedUnknown.java:4)，父类 Signature、符号 Methodref、BCI 及 `@method relay(I)Ljava/lang/Object;` 在 JSON 对应记录。

- **VarargsCall（GC-08）**：四腿原源码声明 `@SafeVarargs public final <U> U first(U... xs)`，relay 使用显式类型实参 `this.<T>first(x)`；调用 receiver 是 `this`。input javap 中 `first` 带 `ACC_VARARGS`，物理 descriptor 为 `([Ljava/lang/Object;)Ljava/lang/Object;`；relay 在 BCI 7–8 将参数装入数组，BCI 9 `invokevirtual first(Object[]):Object`。候选发射 `first(Object...):Object` 和 `relay(Object):Object`，均标拒绝，调用表达式成为 `this.first(x/arg1)`，省掉显式 `<T>`；行为通过、反射不匹配。边界理由：varargs 适用规则与编译器的数组实参构造不能当作普通固定参数 direct-call substitution；即使 descriptor 可读，也需要证明方法 varargs 标志和真实调用形式没有被忽略。可定位证据：[VarargsCall.java:13](../candidate/candidate-v3/gc01-08-140/openjdk23/debug/VarargsCall/jarde/VarargsCall.java:13)，方法 flag、数组构造及 BCI 见 JSON 对应记录。

SameErasureBinder、MultiUseResult 的拒绝判据已有各自 pass 结果，不属于上述七个待 root 复核项；BridgeUnknown 与 IncompleteSite 是正控制，未并入拒绝项。candidate-v1 的 `root-control-disposition-v1.md` 是历史 CLI 裁定，不能直接代替 candidate-v3 的逐项验收。
