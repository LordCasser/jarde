# 固定 CLI5 控制事实（GC-04/05/08）

本页对应固定 CLI5 的 140+4 完整重放，只列物理与源码事实，不替 root 作最终裁定。四腿为 Corretto 8 / OpenJDK 23 × debug / nodebug。逐腿输入 jar、源码、Probe、candidate 完整源码、物理 javap、Probe 反射/行为和哈希见 [candidate-v5-control-facts.json](candidate-v5-control-facts.json)，SHA-256 `fbc51c9c9f7e8b54f8dff4978330bc0399bb004c4c4dd55e2c533068e9dcc0d4`。七项仍由固定 runner 的 `CONTROL_REVIEW_ONLY` 留待 root 复核；编译与 Probe 通过不等于拒绝判据正确。

- **UnknownIncoming（GC-03/08）**：原源码包含 `identity(T)`、`safe(T x) { return identity(x); }`、独立 `untouched(T)`，以及 `unsafe(Object x) { return identity((T)x); }`。safe / unsafe 的 receiver 均为隐式 `this`；物理输入在不同方法中有调用 `identity(Object):Object` 的 invokevirtual。CLI5 四腿 candidate 保留 `untouched(T)`，identity/safe/unsafe 都是 Object 头并有拒绝标记，但原因现不完全同：identity 标记 incoming-use 闭包未证明；safe 与 unsafe 标记 ordinary generic source 未证明。候选 call 写为 `this.identity(x)`（nodebug 局部形参名可能不同）。Probe 行为 `safe+unchecked+independent` 保持一致，完整反射不匹配。能支持的是 incoming unchecked/Object 路径与普通泛型 AST/SSA 证明边界需 root 检查；不能只凭 marker、行为或编译得出闭包正确。代表 candidate：[UnknownIncoming.java:13](../candidate/candidate-v5/gc01-08-140/openjdk23/debug/UnknownIncoming/jarde/UnknownIncoming.java:13)。

- **CycleRelay（GC-08）**：原源码的 `left(T, boolean)` 与 `right(T, boolean)` 条件分支互相调用，else 分支直接返回 `x`；receiver 为隐式 `this`。CLI5 candidate 将调用展示为 `this.right(x, false)` / `this.left(x, false)`，两个方法的最终头均为 Object，且各自标记 ordinary generic source 未证明。输入 classfile 有相互指向的 invokevirtual，descriptor 为 `(Object,boolean)Object`。四腿 Probe 行为一致而反射不匹配。物理环证据说明路径有限化需要谨慎，不能让相互待证类型形成循环证明；拒绝本身是否充分仍需 root 裁定。代表 candidate：[CycleRelay.java:13](../candidate/candidate-v5/gc01-08-140/openjdk23/debug/CycleRelay/jarde/CycleRelay.java:13)。

- **MethodHandleUse（GC-08）**：原源码在 `relay(T x)` 中保存 `Function<T,T> f=this::identity` 后调用 `f.apply(x)`；方法引用 receiver 是 `this`，`apply` receiver 是局部 `f`。物理 classfile 有 invokedynamic / LambdaMetafactory bootstrap，MethodHandle 指向 `identity(Object):Object`；relay 对函数接口的实际 invoke 是 `invokeinterface Function.apply`，不是直接 invoke identity。CLI5 candidate 保留 `this::identity` 和 `f.apply(x)`，identity 标记 same-class binding 未证明，relay 标记 ordinary generic source 未证明，最终头均为 Object。行为一致、反射不匹配。bootstrap handle 不应被当作本片直接 invoke caller→callee 证据；实际 collector 是否正确排除仍需 root 查看。代表 candidate：[MethodHandleUse.java:13](../candidate/candidate-v5/gc01-08-140/openjdk23/debug/MethodHandleUse/jarde/MethodHandleUse.java:13)。

- **RawOwnReceiver（GC-05）**：原源码显式声明 raw 局部 `RawOwnReceiver raw=this`，调用 receiver 的静态类型就是 raw 局部；随后通过 `(T)raw.identity(x)` 返回。CLI5 candidate receiver 形状为 `this.identity(x)`，identity 与 relay 都生成 Object 头；identity 有 incoming-use 拒绝标记，relay 有 ordinary generic source 未证明标记。四腿输入物理调用为 `invokevirtual identity(Object):Object`。边界理由是 raw receiver 的成员选择不能借用 class `T`；要由 root 核对 AST/源码中的 raw 类型事实实际进入拒绝判据。编译和 Probe 行为通过、反射不匹配，marker 本身不构成 receiver 证明。代表 candidate：[RawOwnReceiver.java:21](../candidate/candidate-v5/gc01-08-140/openjdk23/debug/RawOwnReceiver/jarde/RawOwnReceiver.java:21)。

- **ReboundOwnReceiver（GC-05）**：原源码的 receiver 变量声明静态类型始终是 `ReboundOwnReceiver<T>`；其后 `Object alias=receiver`，再将 `(ReboundOwnReceiver)alias` 赋回 `receiver`。raw cast 赋值是 unchecked assignment，但不会把原变量声明类型变成 raw，因此不能据此说原源码最终调用必然按 raw receiver 选择。物理 classfile 有 checkcast 与 `invokevirtual identity(Object):Object`，但没有该局部变量的泛型静态类型。CLI5 candidate 四腿源码则实际声明 raw 局部 `ReboundOwnReceiver receiver`（nodebug 名称可能变为 `local2`），保留 Object alias / raw cast 重绑定后再通过该候选 raw 局部调用 `receiver.identity(x)`；identity / relay 最终头为 Object。支持 root 复核的拒绝边界是未证明的 Object alias/raw cast/重绑定及 candidate 的 raw 局部声明；不能以原源码最后调用必然 raw 选择为依据。完整四腿 candidate 源文和实际局部声明在 JSON。代表 candidate：[ReboundOwnReceiver.java:21](../candidate/candidate-v5/gc01-08-140/openjdk23/debug/ReboundOwnReceiver/jarde/ReboundOwnReceiver.java:21)。

- **InheritedUnknown（GC-08）**：原源码是 `InheritedUnknown<T> extends ArrayList<T>`，`relay(int index) { return get(index); }` 的 receiver 为隐式 `this`。candidate 因参数化父类未证明而输出 raw `ArrayList` 父类，relay 头为 Object，调用写作 `this.get(index)` 并有 `T` 不在可用 Signature scope 的拒绝标记。输入 BCI 处的 invokevirtual 符号 owner 是 `InheritedUnknown.get`，但物理类没有 `get` 声明，父类才是 `ArrayList<T>`。Probe 行为一致、反射不匹配。符号 owner 名称不等于方法声明属于当前类；继承成员代换边界需单独证明。代表 candidate：[InheritedUnknown.java:4](../candidate/candidate-v5/gc01-08-140/openjdk23/debug/InheritedUnknown/jarde/InheritedUnknown.java:4)。

- **VarargsCall（GC-08）**：原源码声明 `@SafeVarargs final <U> U first(U... xs)`，relay 显式以 `this.<T>first(x)` 调用，receiver 为 `this`。输入 javap 保存 `ACC_VARARGS`、descriptor `([Ljava/lang/Object;)Ljava/lang/Object;` 和对此 descriptor 的 invokevirtual。CLI5 candidate 保留 `first(Object...)` 形状，但 first 与 relay 的头为 Object，标记 same-class binding / ordinary generic source 未证明；调用表现为 `this.first(x)`，显式 `<T>` 不在 Java source rendering 中。Probe 行为一致、反射不匹配。varargs 适用规则和数组 descriptor 必须与普通固定参数推断区分；拒绝边界仍由 root 裁定。代表 candidate：[VarargsCall.java:13](../candidate/candidate-v5/gc01-08-140/openjdk23/debug/VarargsCall/jarde/VarargsCall.java:13)。

另外四项角色分开保留：SameErasureBinder 的固定拒绝控制谓词为 4/4 pass；MultiUseResult 的 atomic-erased-fallback 拒绝控制谓词为 4/4 pass。这两个是固定控制判据结果，不计为 API 恢复成功。BridgeUnknown 四腿是 positive bridge/boundary control，IncompleteSite 四腿是合法 single-call conditional positive；两者均不能混成拒绝样本。完整矩阵状态为 `needs-review`，summary 与逐腿 manifests 见 [candidate-v5-acceptance-summary-zh.md](candidate-v5-acceptance-summary-zh.md) 和 [candidate-v5 run manifest](../candidate/candidate-v5/run-manifest.json)。
