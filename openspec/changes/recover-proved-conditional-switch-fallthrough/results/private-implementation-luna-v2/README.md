# Conditional switch fallthrough implementation draft (private, unrun)

This is an un-applied source patch draft against the unchanged `region.rs`, `build.rs`, and `report.rs` captured in `before/`. The earlier blocker/architecture audit is preserved at `/private/tmp/jarde-proved-conditional-switch-fallthrough-implementation-v1/blocker-audit-v1.md`.

The representation boundary is real: the existing `SwitchGroup::fall_through` controls the whole arm's tail, while `Frame::switch_arm` only stops ownership at another label or the common join. It cannot say that one conditional route falls into the next label while its sibling exits the switch. The Region `If` also does not record an edge destination for an empty arm. Probing the richer map alone therefore cannot produce the mixed `if` safely: the normal arm-walk gate still refuses an arm that ends at the switch join without a represented transfer. The minimal missing fact is a zero-block `Region::SwitchBreak` carrying the transfer/branch BCI, owning switch BCI, and canonical join identity. The patch emits it only after the canonical path checks, and Builder consumes it only under the current nearest switch context and unchanged loop/switch depth, as the existing unlabelled `StmtKind::Break`.

The patch has three source files: `region.rs` carries and validates the switch-break leaf and the bounded conditional path certificate; `build.rs` scopes the switch target while rendering arms and handles the leaf; `report.rs` preserves the leaf's physical source BCI when the leaf owns no block. It does not change emitter syntax. `after/p3_conditional_switch_fallthrough.rs` is a permanent-test draft using the frozen complete 1563-byte upstream class, including its real `check()` and nested class bytes; it expects exactly two join-transfer breaks (BCIs 89 and 114), case 2 once, and no loop rule.

`tests-draft.md` records the negative and budget cases still needed. The drafts have only been read and edited as text. No Rust parser/compiler, formatter, Git, Cargo, JDK, CLI, or test process was run. Treat the patch as unverified: root must review it, copy/apply it in the planned sequence, and run focused real-class, negative, cancellation/budget, and regression tests before considering it.
