# Conditional constructor values: private Java 8 controls

This private v2 keeps the two target classes from v1 and adds only Runner cases. It is a small, uncompiled control set for `recover-proved-constructor-conditional-values` task 1.2: two independent target classes and one finite Runner. The sources use `java.lang.String`, have no explicit static initializers, helper/nested classes, anonymous classes, or non-JDK constructor dependencies. `manifest.json` lists only the two intended top-level target classes.

`ConditionalConstructionPositive` isolates a direct conditional value used by a return or field store. The one-arm method chooses between `new String(argument(...))` and the original reference; the two-arm method has separate constructor expressions. The argument helper logs event 2 after the condition helper logs event 1, and each can throw. Runner now includes selected `new String(null)` and the corresponding unselected-null reuse case, so it records the constructor failure separately from a helper failure. Static and instance field cases cover both arms; another static field case records the slot and event counters if the selected argument throws before assignment completes.

`ConditionalConstructionRefusals` is a set of boundary probes, not a class expected wholesale to refuse recovery. In particular, `localBoundary` may compile as a stack Phi followed by a local Store, and existing Store support may recover it. `independentBranchEffect` may remain a structured `if` with its branch effect rather than become a conditional expression. The handler case is a refusal only if the actual control-flow/exception edges prevent the relevant proof. The shared field-and-return and nested-conditional methods probe the stated shared-output and nesting boundaries. These are source-level intentions; their emitted IR and recovery outcomes remain unobserved.

Runner catches `Throwable` around each target invocation and prints values, object-identity comparisons, exception classes, and event/call counters. Inputs and cases are fixed and finite; there are no loops. Any expected relationship is an inference for the later capture, not an observed oracle. No bytecode shape, Jarde rendering, compilation result, or runtime output has been obtained for these new sources. Root should compile and capture both JDK legs, then compare the original classes' actual outputs before using the controls as evidence.
