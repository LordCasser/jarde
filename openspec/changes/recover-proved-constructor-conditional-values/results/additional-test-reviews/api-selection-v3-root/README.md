Private review candidate only. `recover_proved_conditional_constructor_values.rs` is copied from the current shared test and edited here; the shared test is unchanged. This preparation did not run Cargo, a Java toolchain, Git, or the test binary.

The root-owned v5 focused run has 2 passing and 3 failing tests. Its raw stderr shows both range tests fail only at whole-class text equality, while the target method bodies are the requested selected/full body; other short members are rendered with `jre_evidence_range_invalid`. The X4 case reaches the assertion that expected `fallbacks` to be nonempty, but the field is empty. Late-stop and four-method positive tests pass in that run.

`class_source_with_evidence` carries one evidence request into each method's recovery run. A BCI interval valid in the selected method may be invalid against another member's own instruction boundaries. The patch keeps strong target checks: body and member-row text, summary/refusal diagnostics, exact physical method identity, UTF-8-safe projected map, source origin at the selected BCI, and selected or empty `NewRecord` payload. It then names the exact non-target members that refuse that interval and requires their stop code, requested interval, unproduced body/map/content/records, and `NotPerformed` evidence; other non-target code bodies must remain complete. Current v5 output identifies `<init>` and `<clinit>` for `UpstreamSequentialLoops2`; for the excluded range on `ConditionalConstructionPositive`, it identifies `<init>`, `condition`, and `argument` as invalid while the other members remain valid.

There is a separate contract tension to keep visible: `class_source_with_evidence` currently documents that assembled class text does not depend on selection, while these actual range outcomes change non-target member text when that same per-body range is invalid. This candidate records the observed method-local refusal and keeps the selected target assertions strict; reconciling that broader API-documentation claim is outside this test-only preparation.

The X4 candidate distinguishes the quality plane from the Region fallback list. The pinned prior X4 API capture for this exact 1400-byte fixture reports `Representation::Mixed`, `Quality::Fallback`, `RecoveryContent::ExplanationOnly`, structured regions, and an empty `fallbacks` list. In `report.rs`, the quality plane becomes Fallback when the recovered body is not structured, including the final program's ragged build; the `fallbacks` vector is populated from `Recovered::fallbacks()` and therefore reports Region-level fallback reasons. These are separate facts. The revised test asserts the committed explanation-only artifact, its quality/representation, nonempty structured regions, and the exact three unpresented record refusal codes (`jre_new_shape`, then two `jre_new_conditional_not_emitted`) plus the unchanged summary. It does not infer Java construction from a text substring.

The old X4 raw capture is provenance for understanding the API planes, not evidence that the current v5 test passed. The v5 failure remains preserved and pinned as the current failure record. Root should run the candidate using its own authorized toolchain flow.
