## Blocking defect

`collect_baseline.py:189` constructs the control path using `Path(__file__).with_name('controls/src/jadx/tests/integration/loops/NestedLoops2GenericControls.java')`. `Path.with_name` accepts a single basename; this argument contains path separators and raises `ValueError`. The referenced file does exist at that relative path, but this expression cannot reach it. This line is before the capture `try` at line 246. The script has already created the output tree and copied files at lines 165-186, but has not written `execution.json` yet (line 230 is later), so the first collector run will stop before any recorded command and leave an output path that a retry refuses as existing (`114-117`). Minimal fix: `Path(__file__).parent / 'controls/src/jadx/tests/integration/loops/NestedLoops2GenericControls.java'` or equivalent; also move setup that can fail after output creation under the guarded/finalized section, or validate all setup pins before creating `out`.

## Driver and oracle

The driver defines exactly ten finite cases (`driver/TestNestedLoops2Driver.java:62-73`) and invokes all on one target instance (`99-105`), so `short-after-long` can expose instance state. It checks a parentless loader and exact CodeSource root (`86-98`), records list `size/get` events and the target's actual return or thrown exception, and the parsing regex/order checks in both collectors match the emitted row shape (`collect_baseline.py:87-101`; generated collector `102-113`). Null list, null element, heap pollution, throwing `get`, throwing `size`, and event order are covered. The logger has an event cap, but throws `AssertionError` at `driver:39-41`; `invoke` catches every target exception and treats its cause as an ordinary observation (`81-84`). If the cap fires, the harness emits a normal `AssertionError` row rather than failing as a harness-limit breach. Minimal fix: distinguish the event-limit sentinel after reflection and exit nonzero (or keep a separate overflow flag checked by `main`) so an overlong/runaway call cannot become an oracle row.

The JDK 8 full-source boundary is actually attempted on the exact full upstream source (`collect_baseline.py:247-259`); its major-55 diagnostic is recorded. It is not asserted, so only the raw command result can establish that the expected boundary was observed. The README correctly presents this as an observation rather than a guaranteed compile failure. Java 23 `--release 8` builds both debug profiles and checks class major 52, outer/child tree, and the child's exact two-method inventory (`261-290`). The default JVM stack is retained: runtime commands do not set `-Xss`, and the wrapper invocation uses the pinned timeout/guard. Guard stop rows are checked by the shared command helper.

## Collection closure and JSON fields

The baseline requests the eight child/bundle-child × default/all class-source cells for each successful source profile (`collect_baseline.py:363-400`). It uses the original compiled outer+child bundle, preserves full Jarde text/raw reports and all JADX `.java` outputs, and records physical method/BCI summaries. The generated collector requires the full 8-cell grid and both JADX profiles, compiles the full source cells with an empty source path, validates Java 8 classfiles, and runs only the generated output root; runtime application classpath is the separate driver directory. It validates dependency artifact and class-directory pins and rejects target binary names from those dependencies (`collect_generated_matrix.py:143-175,230-249,261-305`). Thus the execution path does not intentionally mix the original target classes into generated runs. Compile failures remain recorded with no runtime rows, and per-runtime semantic mismatches are stored as `matches_original_profile_runtime: false`, not counted as passes.

A nonfatal JSON-path mismatch makes part of the promised summary empty: `collect_baseline.py:388-394` reads `owner`, `location`, and `variant` directly from `method.item`. In the supplied API sample, `item` has `identity`, and these values are nested under `item.identity.owner` (`owner.location` and `owner.variant`); the current summary emits `None` for those three fields. `name`, `descriptor`, `outcome.report.quality/fallbacks/regions/source_map`, and top-level `api.text` do match the captured shape. Minimal fix: read the nested identity owner fields, and validate their presence instead of silently writing nulls.

A second readiness weakness is status validation. Baseline status becomes `captured-pending-independent-review` without requiring both JDK 23 profiles, four successful original runtime rows, a complete eight-cell Jarde grid, parsed method inventories, or a successful wrong-root control (`collect_baseline.py:314-400,429-442`). The generated collector later rejects many missing cells/oracles (`collect_generated_matrix.py:134-153`), but the baseline receipt can still look complete before that stage. Minimal fix: before assigning captured status, require the exact expected profile/runtime/API grids and wrong-root result; keep the JDK 8 boundary outcome observational. Also validate `methods` is a list with unique `(name, descriptor)` keys before building `physical_method_inventory`; the downstream parser only uses a set/subset check (`collect_generated_matrix.py:81-83`), which would hide duplicate method rows.

## Scope that is covered

The separate control source is pinned and rechecked, not compiled or run by these collectors; the README states that boundary. The primary source is copied byte-for-byte and compiled whole, preserving the JUnit outer class. The class-source request cells use the selected child class plus its complete outer/child bundle, and generated JADX cells copy every emitted Java source. The JDK manifest, compiler/runtime binaries, CLI/JADX binaries, parser and guard helpers, source inputs, and command streams have pins. The noted `with_name` failure currently prevents any of these runtime and source-profile checks from being exercised by the baseline collector.
