# Candidate v1 adversarial review

Scope: `/private/tmp/jarde-indexed-list-signatures-impl-luna-v1-20261019/changes.patch` (not integrated or built). The candidate's own README correctly marks execution pending. I read the patch and its changed files plus current unchanged decoder/build implementation. No test/build execution.

## Findings

1. **Build blocker; primitive path is in the wrong generic-declaration branch.** In candidate `repo/src/class_source.rs:8842-8853`, `primitive_complete_body_result_proved` calls `result.as_deref()`. In this function `result` is the chosen method-local generic result spelling (`&str`, set at lines 8746-8761), not an `Option`; this cannot compile. More fundamentally, this is `generic_method_declaration`, whose non-void path requires a method `TypeVariable` result, so a primitive result must not be admitted there. Minimal correction: remove this new primitive-result clause and retain CompleteBody-as-void-only here. The ordinary parameterized gate at `:7571-7580` is the appropriate place for the primitive extension, where the parsed Base and descriptor result are compared.

2. **The cast target has an adequate same-run provenance chain, but the new AST query does not close its own physical opcode.** `decode::check_cast` reads the physical instruction's CP Class name into `Operation::CheckCast` (`crates/jarde-java/src/decode.rs:824-834`); normal AST recovery turns that exact operation into `ExprKind::Cast { ty }` with `Origin::direct(bci)` (`build.rs:29337-29371`). Thus `ty == element_type` is not a guessed/presented AST type: for this unchanged retained AST it comes from that checkcast's CP target. The get branch adds no body or cast projection edit (`facade.rs:14752-14759`), so the retained physical Cast type is not subsequently rewritten. Facade separately ties the same BCI to one `SameClassBodyValueSite` with effective physical opcode `0xc0` and SSA input/output (`src/facade.rs:14740-14749`). I do **not** see a need to add another CP-target field solely to duplicate that evidence. However, `class_source_exact_cast_call_child` itself only checks that the BCI is present (`report.rs:2264-2285`); have it also require the uniquely retained `class_source_instruction_opcode(ast, cast_bci) == Some(0xc0)` and direct primary provenance, or keep the helper strictly internal to the caller that already closes the physical row. `source.instruction_opcodes` is retained for this distinction (`report.rs:8344-8351`). A missing `Origin.method()` is normal for `Origin::direct`; the `ClassSourceMethodAst`'s `source.member` is the binding context, so do not reject that normal unbound form.

3. **Repeated whole-AST scans amplify work for each `get`.** The facade first resolves its selected call set in one batch, then the `call_kind == 5` branch invokes `class_source_exact_cast_call_child` once per `List.get` read (`facade.rs:14752-14755`). Each invocation calls `class_source_invoke_ast_sites` (another whole-tree scan) and then recursively walks the whole tree again (`report.rs:2287-2322`). `charge_class_source_ast` counts the retained tree before charging it (`report.rs:5471-5500`), and neither recursive walk polls per node. This is charged and therefore bounded, but an otherwise supported method with many gets pays roughly two complete AST scans per get and can hit limits or delay cancellation. Minimal correction: reuse the already validated batched call sites and prove the `(call BCI, cast BCI, expected type)` relations in one batch AST traversal; include polling during that traversal. Avoid introducing a general visitor framework.

4. **Nested concrete element signatures are silently reduced to the last class segment.** `generic_list_parameter_types` accepts a multi-segment element but constructs its AST type from only `element.segments.last().binary_name` (`facade.rs:13026-13050`). For a signature such as `List<p.Outer.Inner>`, this drops `p.Outer`; the real physical cast target is the nested class, so the exact cast check will refuse a valid candidate (or mishandle name collisions). Minimal correction: use the existing whole-signature spelling path for the element or conservatively decline multi-segment element signatures before constructing a type. This is a false refusal, not evidence of unsafe acceptance.

## Positive checks

- The physical `List.get:(I)Ljava/lang/Object;` call is selected by exact owner/name/descriptor/opcode; its result must be unreplaced, defined at that invocation, and have one BCI use. The cast row must be unique, consume the same SSA value, write a fresh unreplaced value, and occur later.
- The AST direct-child test retains the cast; it does not delete or re-type the expression. The call is independently resolved against the same AST's exact invoke inventory, and foreign method origins are refused.
- `CompleteBody` primitive admission is restricted in the ordinary Signature gate to an exact primitive result plus complete body/parameter proof and at least one proved concrete List formal. Existing void, method-local type-variable, and special-return gates have explicit `result_type: None` checks where required. Stage and final recompute and compare the List proof vectors; Stop errors propagate rather than publishing a partial generic component.
- One fixed boolean regression is added, but it does not exercise the new int/long/void paths or the wrong-cast/extra-use/AST-missing/Stop controls called out by the candidate README. Those are still needed before acceptance.
