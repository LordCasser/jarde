## Integration assessment

I found no additional type-soundness blocker in the core v2 changes beyond the small integration fixes root already identified. The primitive `CompleteBody` gate remains separate from method-local type-variable declarations: the candidate carries the physical result type, the ordinary gate checks exact physical type, descriptor spelling, and Signature spelling, while the old generic-method branch still accepts only `result_type: None` (see `class_source.rs` around 5410 and 7587–7607, 8690–8872). Parsed List element types come from the method Signature and exact slots; they are not inferred from `get`. For `List.get(I)Object`, the proof requires an unreplaced result defined at that invocation with one physical cast use, exact same stack-input fact at a unique `0xc0` body row, and an iterative AST match for the direct retained `Cast(E, Call(get))`, with unique anchors and no foreign origin (facade around 14759–14775, 14900–14940; report around 2253–2380). The AST Cast type is produced from the same physical CheckCast operation; the direct origin and same-BCI opcode check bind it to that instruction, so a second CP/type-fact model is unnecessary. The normal list Signature gate also compares any add-derived local types with the parsed element type. The staged and final presentation-removal vectors are compared before commit (facade around 19129–19134); budget/cancellation errors propagate through the existing transactional error path.

The prior concerns already reported by root are separate: the tests-only `pure_method.evidence` compile typo, skipping the cast-call batch traversal when there are zero get relations, and removal of the newly added single-item wrapper. Do not treat this review as saying those fixes are already applied to a shared checkout.

## Findings

**P2 — the bulk complexity reservation is charged as IR storage.** `prove_generic_list_parameter_body` computes `(reads + receiver_calls + 1) * scan_bound * 8` and charges that value to both `AnalysisSteps` and `IrItems` before the scans (facade lines 14820–14839). The subsequent loops produce only linear-sized worklists; the product mostly bounds repeated searches, not derived storage. `CountedBudgetDimension::IrItems` is documented as derived storage items charged before allocation, while `AnalysisSteps` is the work counter (reader budget source pin in `pins.json`). Applying the product to IR item limits can stop an otherwise valid method with many List uses even when actual allocations remain small. The exact single-request defaults are 2^22 for each dimension (`src/facade.rs` near line 45150). Minimal correction: use per-iteration `AnalysisSteps` charges for the actual search loops and charge `IrItems` only before each actual worklist/vector item allocation (or a tight item-count precharge).

**P2 — one filtered traversal delays cancellation polling over skipped rows.** The initial `parameter_receiver_calls.iter().filter(...)` loop polls only after the filter yields a selected List row (facade lines 14841–14860). If an unselected prefix is long and cancellation/deadline arrives while that prefix is scanned, the loop does not observe it until a matching row. The work is bounded and included in the up-front estimate, so this is a responsiveness issue rather than unmetered work. Minimal correction: use an explicit loop and poll/charge before examining every row, then continue for nonselected slots. Similar `find`/`filter` scans inside per-read proof loops should be charged per examined element rather than relying solely on an upper-bound reservation if the reservation is removed.

The batch AST query’s requirement that its relation array be sorted by both call BCI and cast BCI can conservatively refuse a legal bytecode shape when those orders differ; the facade sorts by call then cast and rejects duplicate call anchors. I did not find that ordering in the fixed javac controls, and it does not accept an unsafe projection, so I classify it as a scope limitation rather than a blocker.
