# O6（任务 2.6）：预热/预取的评估与暂缓依据

## 1. 调查的问题与假设

**问题**：在固定导航序列与放弃序列上，提前安排工作（预热/预取）能不能在**总计算不增加**的前提下改善前台等待；
如果不能，缺的是需求还是证据。

## 2. 测量形状

| 来源 | 形状 | 样本 |
| --- | --- | --- |
| 本轮新测 | W2 固定导航序列（8 个类 + 1 次控制重问）、W4 放弃序列（取一页即丢弃 cursor）；两语料各 5 个独立进程 | `investigation-*-raw.jsonl` |
| 引用 G0 | W1 的 `prepare`（调用方发现）与 W4 的首屏读数 ×10 | 引用 |
| 源码事实 | `prefetch`/`warmup`/预热在 `src/**` 与 `crates/*/src/**` **零命中**（`rg` 全仓），即当前没有任何预热入口 | 本轮核对 |

**没有为 O6 新增工作负载**：产品里没有可开合的预热路径，先测「预热」会变成测一个不存在的功能。

## 3. 必要工作证据（p/s/h）

| 读数（fixture / bcprov） | 值 | 与预热的关系 |
| --- | --- | --- |
| 导航一次类（W2 逐请求中位数） | 15 µs / 15 µs（min 4 / 7，max 59 / 1,225） | 预热能省的单位就是这个量级 |
| 同一序列的控制重问 | 16 µs / 19 µs | 重复访问已经很便宜 |
| 冷首问（bcprov 的 W2 max） | — / **1,225 µs** | 首次访问真正贵的是容器/绑定，不是「第 N 个类」 |
| 调用方发现（W1 `prepare`：load root + 类声明清单） | 813 µs / **256,334 µs** | 这是**已经**在请求之前支付的、与目标数无关的一次性成本 |
| 放弃序列一页（W4，一页后丢弃） | 18 µs / 40 µs | 前台等待本身已经很小 |
| 整段小页序列（W4） | 978 µs（13 页）/ 538,530 µs（548 页） | 放弃只剩 1.8% / 0.008% 的序列成本 |

**如果宿主预取 k 个类而只用到 1 个**：按 W2 的逐请求分布，8 个类的总成本 ≈ 1,225 + 7×15 = 1,330 µs（bcprov），
而只问 1 个类是 1,225 µs——**多做的 105 µs（8% 的导航量）在总计算上没有任何回收**，因为：

- **预取事实不会让后续请求少做它自己的事**：W1「同 snapshot 第二次同请求」的 `count_class_materializations`
  仍然是 **1**（O2 的表），即需求路径每次请求都重做受信读取；
- 预取能省的只有容器目录/绑定那一部分（`with a store: archive_entries=3 … without: 5`，d2 门禁），
  而这一部分正是**调用方已经通过 store 拿到的**，不需要新机制。

## 4. 理想上界

- 导航带的完全消除上界：8 个类的 1,330 µs 全部提前或删除，前台只剩「拿结果」——即 **≤1.33 ms/8 类**
  （bcprov，占 W5 单次请求流量的千分之几）。若目标只是「下一个类」，上界更小（15 µs）。
- 折算成 design §1 的形式：无条件预热的期望工作量 = `(1−q)·C`。本工作负载上 `C` = 15 µs/类（导航）、
  `q` 由宿主轨迹决定且**没有实测**；`q=1/8` 时多做的期望工作 ≈ 7/8 × 8×15 = 105 µs。**p 无法算**：
  没有声明的前台延迟目标（design §9 的前置条件本身缺失）。

## 5. 资源与语义代价

- 若把预取做成「提前构造并保留」：它会落在 O5 的同一个 `FactsCapacity` 字节界上，
  而当前 CP/Header 层在 bcprov 上已经用到 8.7 MB 量级（W5 roomy 的 2430 entries）；预热必须与前台共享预算。
- 语义风险（design §9）：预热**不得扩大前台请求的 coverage**、不得隐式启动全局 Body 读取、
  不得把「取消/失败」藏成前台 cache miss 后的无限重试；这些在没有实现之前只能作为前置约束登记。

## 6. 负向实验与结果

- **负向 1（「预取让后续请求免费」必须被证伪）**：如果预取真的免掉了后续工作，
  W1 第二次请求的 `class_materializations` 应为 0。实测为 **1**（O2 表，两语料一致）——
  这条把「预取 = 让后续请求不做读取」判为**不成立**。
- **负向 2（提前支付不得计成节省）**：W2 的逐请求序列可直接相加核对（`per_request_micros` 40 次调用，
  fixture 中位数 15 µs、bcprov 中位数 15 µs，冷首问 1,225 µs）。若把 8 类都算成「省下」，
  总时间反而从 1,225 涨到 1,330 µs；门禁口径由 G0 的账本持有（阶段互斥、不重复归因）。
- **负向 3（放弃序列的成本上限）**：W4「一页即弃」18 / 42 µs，而整段 978 / 538,530 µs——
  提前做完的 99% 工作会被丢掉；这条用于否决「无差别预取整棵树」。

## 7. 处置建议

- **暂缓 O6**，理由是**缺需求 + 缺前台延迟目标**，不是缺实现。
- **重新进入条件**（可观察，沿用 design §9 与本轮读数的量级）：
  1. 出现一个**宿主显式声明导航轨迹**的场景（例如一次会话里给出目标类列表或「下一个类」信号），
     且该轨迹的预测命中率 `q` 被实测；
  2. 前台存在**已声明且当前不满足**的延迟目标；按本轮读数，导航带是 15 µs/类、
     一次性发现是 256 ms（bcprov），两者量级差四个数量级，预取只可能对前者有意义；
  3. 有独立的预算/取消模型与在途上限，能与 `FactsCapacity` 共享字节界。
- **不因本条暂缓任何其他候选**：W6a 的类间并行与 W5 的保留都不依赖预热（O4/O7 已独立测量）。
- **不实现**空转的预取接口来「占位」。

## 8. 未确认项

- `q`（预测命中率）没有实测；**未证实**：任何「预热能改善前台」的结论。
- 争用（预热与前台同时跑）没有测量，因为不存在可开合的预热路径。
- 放弃序列只覆盖「取一页后丢弃」一种；「切换到另一个 artifact」的放弃路径在 W1 的 `w1-second-snapshot`
  里有间接读数（再开一个 snapshot 多付 1,329 / 57 µs 请求 + 255 / 0.72 ms 发现），但没有把它当成预热实验。
