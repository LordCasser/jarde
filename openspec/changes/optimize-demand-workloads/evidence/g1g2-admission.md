# 任务 3.1：O1–O8 的 G1/G2 准入矩阵

本文件把 §2 的八份调查（`evidence/o{1..8}-*.md`，摘要 `evidence/o-investigation-summary.md`）折成
design §3 的两个门禁所要求的决定：**G1 必要性**（无关/重复工作的证据，或能解决明确延迟/吞吐/内存目标的
上界）与 **G2 最小实验**（单因素原型、直接路径对照、资源/语义/退化验证）。处置只有三类：**准入**
（有独立实施 change 与已完成的最小实验）、**否决**（含「维持已交付/不重复立项」）、**暂缓**（有可观察的
重新进入条件）。三个平面分列：**契约**（语义与诊断）、**工作量**（计数）、**时间**（墙钟）；
时间层落在离散度内一律记「未证实」，不因工作量成立而升级成时间结论。

数字来源只取三类：§2 八份证据（含其引用的 G0 与已归档 change 门禁）、本阶段 G2 实验
（`evidence/g1g2-experiment-o2.md`，原始样本 `g1g2-o2-raw-{fixture,bcprov}.jsonl`），以及下文标明的
引文。引用项只计一次，见 §3。

## 2. 5% 占比示例核对（design §1 的上界算式）

算式 `S = 1 / ((1−p) + p/s + h)`，`1/(1−p)` 是「忽略额外开销、完全消除该部分」的乐观上界：

| 示例 | 代入 | 结果 |
| --- | --- | --- |
| 5% 阶段被完全消除（`p=0.05, s=∞, h=0`） | `1/(0.95 + 0 + 0)` | `S = 1.0526`，端到端最多省 **5%**，即 `1/(1−p)` 上界成立 |
| 同一 5% 阶段只做到 4× 局部加速且新增 1% 管理开销（`p=0.05, s=4, h=0.01`） | `1/(0.95 + 0.0125 + 0.01)` | `S = 1.0277`，只省 **2.7%**：管理开销会直接吃掉上界 |
| 5% 阶段不可达（`p=0.05, s=1`） | `1/1.0` | `S = 1`，收益为 0 —— 与「收益未证实就记未证实」同义 |

用它逐项核对上界（判据：**乐观上界达不到 5% 的项，不以时间理由准入**）：

- **O8 编码**：`p = 2.8%`（写盘另 3.6%），即使 `s=∞, h=0` 也 `<5%` ⇒ 否决是算术结论，不是偏好。
- **O3 页边界**：`p = 7.5%` **只在 2 条/页**成立；默认 64 条/页时 18 个边界 ≈0.3%（278 ms × 18/530）
  ⇒ 默认配置的乐观上界 `<5%`，而 2 条/页是调用方用法而非默认路径。
- **O2 读取**：本轮实验的端到端上界是「整个 W1 请求段 1.36 ms（bcprov，窗口 275 ms）」，即窗口的 0.5%；
  5% 的窗口份额是 13.8 ms，比一次读取高三个数量级 ⇒ **时间层不可能成立**；design §3 明确允许结构性访问
  范围修正由「不必要工作证据」准入，因此 O2 按**工作量层**准入，准入文档禁止发布加速结论。
- **O1/O5 容器层**：`p` 无分母（请求段与 prepare 不同源），因此本专项对这两条**只**发布计数与驻留上界，
  不发布端到端占比。

## 3. 重叠收益未重复相加（逐对论证）

**3.1 O1 与 O5 的容器层是同一交付物**：O1 证据的 W5 四档（`container_hits` 17538、`directory_parses` 11、
`archive_entries` 70、往返 469 µs）与 O5 证据的容量梯度**逐项相同**，因为两者量的是同一个已交付产品
（归档 `bound-container-lookup`）。引用只计一次；O5 §7 的「容器与 CP/Header 层维持、不重开」与 O1 的
「维持已交付」是同一结论的两种说法。

**3.2 O2 的读取复用与 O5 的容器/CP 层作用在同一请求的不同工作**（必须显式论证，因为两者都在
「第二次请求为什么变便宜」里）：

- 本轮实验把两条路径**同时**开着，读数在中位数（n=10）上逐项对照（bcprov W1 第二次请求）：
  `entry_bytes` 2056 → **0**、`read_bytes` 1165 → **0**、`archive_entries` 7 → **0**、
  `class_materializations` 1 → **0**；而 `class_bytes` 两臂都是 **0**（CP/Header 层的命中两臂相同）、
  `container_hits` 两臂都是 **2**、`directory_parses` 两臂都是 **0**、`nested_materializations` 两臂都是 **0**。
  即：处理组的差**只**集中在读取本身的计费维度上，容器/CP 层在两条臂里逐项相同 ⇒ 不是同一段工作。
- 反过来在容器层被饿死的档位上（W5 `capacity=tiny`，`container_hits=0`、`directory_parses` 28/36），读取复用
  仍然各自生效（bcprov 往返 24,928 → 24,826 µs；fixture 424 → 356 µs）⇒ 两者的收益是同一请求序列里**两个
  不相交的分量**，可以同时存在，但**不能把两份公开上界相加**：O5 公开的 24.8 ms/10 请求与 O2 的 −82 µs/10
  请求（roomy 往返 498 → 416 µs）量的是**同一批 10 个请求**，相加会把同一批请求计两次。正确的陈述是
  组合读数：roomy 往返 416 µs（本轮，两者都开）对 none/tiny 形状的 24,928–25,268 µs。

**3.3 O2 的读取复用与 O4/bulk 的按类形状部分重叠**：bulk 的类形状本身就把「每类读一次」变成默认
（W3 类形状 8 读 4 准备、`request` 600 µs，对逐方法 36 读 36 准备、2206 µs）。本轮在**逐方法臂**上单独打开
读取复用，得到同样的读取删除（36 → 命中 36 次，准备仍 36），`request` 2178 → 1764 µs（bcprov，10/10 对更快）；
而类形状臂仍在 564–598 µs、准备仍是 36/77 对 4/8。因此 bulk 的公开收益（2206 → 600 µs）里**已经含**这 28–36
次读取，把 O2 的节省加到它上面就是重复计算；O2 的独立增量只在**没有按类分组**的调用形状里成立。

**3.4 O8 的编码成本与 O4/O7 的段是同一段**：编码 2.8% 是 W6a `request` 段里的**嵌套**读数
（`sink_encode`，另加 `sink_write` 3.6%），与 O7 量到的窗口等待、O4 量到的按类准备同段 ⇒ 三者不可相加。

**3.5 O7 的 `take_front` 等待不是可加收益**：o7 §4 已声明 `request − take_front` 不能读成可达收益；它是
「最早类优先」的顺序约束，属 bulk 登记的未裁定架构决策，本专项不计入任何组合。

## 4. 决定汇总

| 处置 | 项 |
| --- | --- |
| 准入（1） | O2：选定定义的读取复用（独立 change；最小实验已完成） |
| 暂缓（4） | O3（前置：cursor/coverage/diagnostic 子 spec，归 demand-driven D4）、O5 更高层 store 与淘汰、O6 预热/预取、O7 的 W6b single-flight |
| 否决/维持（3） | O1（维持已交付，F 保持「满则拒绝」）、O4（bulk 唯一负责）、O8 的编码/增量摘要/mmap |
| 不新立但继续跟踪（1） | O7 的 W6a 类间并行（bulk 唯一负责；窗口设计为其未裁定项） |

其余跨条约束：O1 仍由归档 `bound-container-lookup` 唯一负责；O4/O7 归 `add-parallel-bulk-recovery`；
O3 与 O8 的证据产品归 `add-demand-driven-core-results`；本专项**不重复认领**任何实现。
