## Findings

1. **The v2 interface defect is fixed.** v3 consumes the helper's `Option<Decided>` directly, consistent with the helper's signature and the selected decision flow. Its changed `NoType::ConflictingWrites` documentation and message are also more accurate: they say that one declaration was not proved sound or that the selected type was not proved compatible, without claiming that no alternative Java type can hold String and Object. The historical v2 review remains preserved separately and is not retroactively marked accepted.

2. **Occurrence-complete access census is sound in shape.** For a candidate physical slot, v3 walks all SSA instruction reads/writes, checks every access's `reuse.variable_at`, refuses `None`, isolates a proved different `LocalVariable` index, and compares same-identity accesses against `SlotUse` as sorted vectors (not sets), preserving repeated identical occurrences and read/write operand identity. The earlier `slot_uses` omission of unresolved identities and `elided_cleanup` entries therefore cannot silently produce a successful partial read/write set. The exact-Object-store cache also retains unresolved owners so an unmapped possible trigger fails closed.

3. **Catch/header/handler and value boundaries fail closed.** Resource slots are excluded before planning; a `Caught` definition invalidates the write set; a method with any exception table is conservatively refused by this candidate. Every candidate write must have both local-written and stored SSA values of `Value::Ref(_) | Value::Null`, which excludes primitive, Top/Second, uninitialized and return-address states; the first store itself must be a non-null `Ref`. Selected arrays and direct/named array stores are refused. The trigger is only a physical local Store with one Stack input, one Local output and a direct producer proven exactly `java.lang.Object`. At least two writes, one read, and an exact Object return descriptor are required.

4. **Load-to-return proof matches the frozen rule.** It checks each candidate read is the same slot's `Operation::Load`, that the SSA load instruction reads the precise `SlotUse` value and produces one Stack output, that the output has not been replaced, and that the SSA definition's BCI/block is this load. Its complete SSA use list must have one BCI consumer; the indexed instruction must be in the use's block, be `Operation::Return`, read only the same loaded Stack value and write nothing. Any copy, phi, extra consumer or non-return consumer consequently refuses the candidate. The helper runs before the single decision map is returned; Stop propagates through `Result` with charge/poll at all substantive scans, and the caller adopts either the proved Object type or the helper's existing refusal result.

5. **No `consumer.slot` check is needed.** The consumer is a use of the *stack output* of the load, not a local access, so it has no local slot to compare. Candidate identity is checked at the load (`Operation::Load` slot and SSA `reads`), and the consumer edge is checked using the exact `ValueId`, consumer BCI/block, sole Stack read, and no writes. Adding a slot comparison on the Return would be meaningless.

6. **No explicit load/return opcode gate is needed for this established frame-category invariant.** This is not a claim that the pipeline is a full JVM verifier. The existing frame table assigns `Ty::Int` to `iload` and `Ty::Ref` to `aload` (`crates/jarde-jvm/src/frame.rs` around 668–672), checks locals through `read_local` in `apply` (around 1938–1998), and distinguishes `ireturn` (`POP_I`) from `areturn` (`POP_R`) in the opcode table (around 760–764); `pop_ty` enforces the category (around 1097), and an inconsistent frame does not publish normal SSA continuation (`crates/jarde-jvm/src/engine.rs` around 814). Given the candidate's proven reference/null stores, identity-complete reads, SSA load output and Object descriptor, the frame category facts constrain a successful direct read/return to the reference form. The current helper additionally verifies the actual SSA stack edge, so an unrelated consumer slot check is unnecessary. No full class-verification claim is made.

7. **One trigger-boundary bug remains in v3 (blocking before apply).** The Object-store cache loop skips only `bci == first.at`, then treats any other mapped or unresolved Object store as a `later` trigger. An exact Object store with unresolved owner at a BCI *before* the selected first-write BCI therefore can trigger a refusal even though it is not a subsequent write of this candidate lifetime; it may be an earlier unresolved same-slot lifetime. It also makes the `later` field/diagnostic order misleading. Require the Object-store BCI to be strictly after `first.at` before considering owner/ambiguity for this narrow “later Object write” trigger (`bci <= first.at` is not a trigger). Keep the later full same-identity census and refusal behavior unchanged once a legitimate later trigger exists. Root has already requested this precise v4 correction. Until then, v3 should not be applied.

## Cost and remaining acceptance

The method-wide physical Object-store census is lazy and cached once per `decide_types` call. It is justified to find direct Object stores that `SlotUse` omits, including cleanup and unresolved-owner occurrences; every instruction/write and cache observation is charged and polled. It avoids repeating a whole-method scan per candidate local. It is an ordinary ephemeral `BTreeMap`, not an identity service or persistent type mechanism. The implementation reuses the existing array descriptor and direct-producer helpers; it adds no recursive array helper, type hierarchy/LUB, or new pass.

The actual positive/negative generated-source outputs, debug/no-debug API behavior, Stop controls, full-class compile/runtime parity, and wider acceptance remain outstanding. The previous same-IR observation and newly accepted baseline controls support the diagnostic/design inputs only; neither validates v3 or v4.

**Disposition:** v3 closes the v2 compile-interface mismatch and appears structurally aligned with the frozen access/consumer gates, but the pre-first Object-store trigger is a concrete false-trigger/refusal risk. Review v4 after it is frozen; do not treat v3 as implementation accepted.
