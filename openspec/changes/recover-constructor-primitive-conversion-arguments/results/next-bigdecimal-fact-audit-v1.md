# BigDecimal initializer fact audit

## Finding

The first type-specific refusal in both saved BigDecimal legs is the inline `new BigDecimal("1.25")` value at the `Number[]` initializer store. The current bounded JDK 8 table deliberately has no `java.math.BigDecimal -> java.lang.Number` row. `ArrayInitializers` already has two ways to accept a reference element without a new type framework: reuse an existing closed platform/array fact, or consume a selected-snapshot hierarchy proof tied to the exact `aastore` BCI. The BigDecimal constructor itself is presented in both legs, so these reports do not show a separate `new`/constructor-composition failure for that element.

That missing edge is not the only reason the complete `main` fails acceptance. Its report independently refuses a StringBuilder concatenation because `arraylength` at BCI 28 splits the append chain, and reports that the `System.out` field access at BCI 17 was not emitted. The refused array/local assignment then leaves the later local read at BCI 46 unbound. Adding only a BigDecimal widening fact would not establish complete method behavior.

The corrected JADX baseline is semantically successful for this case: after using the actual generated entry class `defpackage.Main`, both JDK legs compile and run under `-Xverify:all`, and both stdout/stderr pairs match the original byte-for-byte. The earlier wrong-entrypoint run is retained but is not the accepted comparison. Across the EM-18 denominator, the root audit reports JADX matches in 18/18 valid legs; that is separate from Jarde, which matches 0/18 overall.
