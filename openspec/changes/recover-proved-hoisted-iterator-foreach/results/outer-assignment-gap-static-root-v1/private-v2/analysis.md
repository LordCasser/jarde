# CF11 outer assignment-first foreach: which proofs already exist?

This v2 keeps the narrow candidate shape from v1 but retracts its proposed mandatory target-owner/type proof. The fixed case's `s1 = (String) local3.next()` is an ordinary local-store statement already emitted by Builder. If the transformation retains that `Assign`, its target, declaration, scope, type decision, all later references, and overwrite order remain exactly as the existing AST built them. Requiring the foreach candidate to reconstruct those same facts from the AST's name would duplicate the normal write pipeline without protecting a changed invariant.

## What the run actually observed

The pinned same-IR diagnostic passed its exact test (1 passed, 0 failed, 0 ignored). Its raw log records only this outer result: at test BCI 13, header BCI 7, path `[1]`, the loop body's first statement was `Assign`; the candidate then refused at `body_first_not_initialized_declaration`. The same-IR dump stops before any outer snapshot, so it did not itself report the outer `Assign` origin, target slot, `LocalVariable`, or SSA writes. Do not call those fields observed from the diagnostic.

Independent frozen evidence gives the bytecode shape: `iterator.next()` at BCI 17, `checkcast java/lang/String` at BCI 22, and `astore 4` at BCI 25. The LocalVariableTable names slot 4 `s1` from BCI 27 through 100. The input source is `for (String s1 : l1)`, and the generated Jarde baseline places blank `String s1;` before the outer while and starts its body with `s1 = (String) local3.next();`. These inputs strongly identify the intended statement, but they are not a same-IR dump of the candidate's fields.

## Existing ownership, declaration, and type invariants

The ordinary local-store path at `build.rs:24024`–`:24090` reads the local slot and stored SSA value from the exact store instruction, calls `write_target(slot, at)`, renders that stored value, and sends the result to `write_statement(variable, name, stored, value, at)`. `write_target` calls `reuse.variable_at(slot, at)` and obtains the spelling from the corresponding `NameTable` identity (`build.rs:25733`–`:25749`; `reuse.rs:84`–`:100`). An ambiguous split-slot store therefore does not become an ordinary named assignment.

`write_statement` checks the expression against the variable's already-decided type before it publishes the write (`build.rs:25532`–`:25602`). It either emits the declaration initialized at this write or routes to `assignment`. `assignment` refuses an unknown declared type and otherwise emits the simple `StmtKind::Assign` with `Origin::direct(at)` (`build.rs:25614`–`:25679`). The local planner's `declare` distinguishes an already-visible declaration, a first write that carries its declaration, and a refused/unknown declaration (`build.rs:25694`–`:25723`). Hoisted declarations are emitted and added to the current `declared` set at their planned region (`build.rs:22944`–`:22975`). Finally, `push`/`push_into` apply the ordinary undeclared-read check before retaining a statement (`build.rs:30220`–`:30249`).

Thus, when the fixed outer first body item is this ordinary store's `Assign`, its existing generated node is already the result of slot/name selection, type compatibility, declaration handling, and undeclared-read publication. Since the proposed foreach change leaves the target name and assignment statement in place, it neither transfers the target to a new scope nor erases any read/write. No separate foreach-only lookup of the target `LocalVariable`, owner placement, `declared` membership, full reader set, or overwrite closure is needed for this preserved-target form. The `StmtKind::Assign` not storing a `LocalVariable` is not, by itself, a missing proof: its producer's exact BCI/slot identity was consumed when Builder created it.

The fixed output's blank `String s1;` and assignment also show how the existing declaration planner handles this example. The assignment is not the declaration site, and it remains in its existing loop-body list. That statement should not be returned among the outer iterator declaration/init removal indices.

## What the iterator candidate already proves for the value

For an inline cast, the existing candidate obtains the first binding statement's expression, unwraps only `Cast(Call(..))`, and requires a zero-argument `next()` on the same iterator local (`build.rs:21550`–`:21579`). It then checks the exact `java/util/Iterator.next:()Ljava/lang/Object;` operation and the iterator's local slot/access identities. The `next()` stack result must have exactly one use at the cast BCI; the cast operation must be `CheckCast`; and its stack result must have exactly one use at `next_store_bci` (`build.rs:21855`–`:21875`). The candidate also requires `next_store_bci` to be an `Operation::Store` (`:21684`–`:21690`). For the fixed ordinary store, Builder gave the statement an origin directly at the store BCI; the stack-use relation and that BCI tie the cast result to the statement's write instruction.

The candidate's existing body rewrite replaces only the `next()` call inside the cast and leaves the enclosing binding statement intact (`build.rs:21977`–`:22007`). Generalizing that small rewrite from `Declare { value: Some(..) }` to `Assign { value, .. }` therefore retains the assignment LHS and the Cast node. `write_statement` already established that the original Cast expression was acceptable for the target's decided type; preserving that explicit Cast keeps the same presented result type while its operand changes from the iterator's Object result to the foreach's Object element. A new target-type equality check is not needed merely because the statement is an assignment.

## Narrow candidate shape and remaining uncertainty

The fixed outer addition can admit only a simple `StmtKind::Assign { value, .. }` at the head, and only when `value` is exactly the inline `Cast` over the already-proved `next()` call. The original target field, statement origin, cast node, and position in `body` stay untouched. Continue to reject compound, field, array, or local-expression assignments; a call/side effect before or after `next()`; non-inline/deferred casts unless a separate existing path proves them; and any next/cast result with another consumer. Do not make “first statement is any Assign” the criterion.

There is no new target-liveness gate for this retained-assignment form: reads such as `s1.equals`, `s1.length`, and `l2.add(s1)` remain the same AST nodes after the same assignment. If a future variant renames `s1` to the enhanced-for header or deletes its assignment/declaration, that is a different transformation and would need whole-local read/write, split-slot, scope, and deletion-owner evidence. It is unnecessary here.

The smallest same-IR follow-up is diagnostic confirmation, not a new proof rule: after opening only the narrow assignment-plus-inline-cast entry path, log the outer binding node's primary origin and expression shape plus the `next`/cast/store instruction BCI, opcode, SSA read/write slots and value IDs. This verifies that the already-existing Builder route actually produced the expected ordinary store node for this method and that the existing single-consumer gates are reached. A target `LocalVariable`/owner dump may help explain that producer path, but it should not become a duplicate acceptance condition. The current diagnostic did not provide these outer fields, and no evidence here claims that the outer iterator Phi/readers/handler gates or a resulting foreach pass.

The `ordinary_generic_source_unproved` report for `test` remains an independent limitation. Nothing in this assignment review predicts or repairs generic signature projection.
