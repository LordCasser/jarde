## Existing proof path that can be retained

`Builder::loop_region` builds the while body into a separate vector, restores the enclosing statement vector, and only then calls `iterable_for_each_candidate` (`build.rs:19023`, `:19100`–`:19245`). A successful projection's removal indices are later applied to the enclosing `self.stmts` vector (`:19264`–`:19270`). The outer assignment itself remains in the detached loop-body AST. This gives a useful boundary: iterator setup declarations/initialization are removed from the active enclosing list, while an assignment-first binding can stay in the loop body.

The early entry condition at `build.rs:21490`–`:21504` only accepts a first `Declare { value: Some(..) }`. The closure repeats that assumption at `:21550`–`:21560`; later it extracts `next()` and optional inline cast at `:21561`–`:21579`. For the fixed outer case, the narrow additional syntax shape would be a simple `StmtKind::Assign { name, value }` whose value is exactly the existing inline `Cast(Call(iterator.next()))` form. The loop candidate can keep the existing iterator-specific proof unchanged: same `hasNext`/`iterator`/`next` interface owners and descriptors; same iterator local identity across init/test/next; same declaration owner and active-list removal rules; same header/next block shape, Phi and exact reader gates, no extra iterator writes, one-consumer `next()` result and cast result, and matching exception-handler sets. The outer run has not yet shown these checks pass.

The inline-cast proof already checks that the `next()` result has one consumer at the cast BCI and that the cast result has one consumer at the store BCI (`build.rs:21855`–`:21875`). The fixed class has exactly that bytecode pattern: `next()` returns Object, the `checkcast String` consumes it, and `astore 4` consumes the cast result. Once the first statement's value is exposed from either a declaration initializer or a simple assignment, these existing checks can validate the expression chain without a separate element-value recovery mechanism.

The post-proof mutation currently requires the first body item to be `Declare { value: Some(..) }` (`build.rs:21977`–`:21995`) and replaces only the `next()` call operand with a synthetic Object foreach element. The minimal assignment-first form can preserve the `Assign` node and its target name while applying that same operand replacement to its `value`: conceptually, `s1 = (String) local3.next()` becomes `s1 = (String) iteratorElement…` inside `for (Object iteratorElement… : l1)`. Keeping the cast and assignment in their original body position preserves the failure point of the cast and the write point of local 4. It also preserves every later read or overwrite of `s1` verbatim, so it does not need a whole-method liveness proof to remove or rename `s1`.

## Minimal new target-local facts

The existing iterator declaration proof cannot be reused as the element binding proof: its `slot`, name, type, and owner belong to local 3, while this assignment writes local 4. The current generic store path uses `write_target(slot, at)` to obtain the split-aware `LocalVariable` and name (`build.rs:25733`–`:25749`), and `reuse::Plan::variable_at` returns no identity when a split slot cannot be placed at that BCI (`reuse.rs:84`–`:100`). `StmtKind::Assign` contains a name and expression but no `LocalVariable` field (`ast.rs:769`–`:770`). Therefore the candidate needs a small cross-check for the assignment target rather than trusting same-spelled names:

- The statement's primary origin must be the exact `next_store_bci`; that BCI must be a local `Operation::Store`, and its `SsaInstruction` must write the same local slot/value that the candidate treats as the cast result.
- `reuse.variable_at(target_slot, next_store_bci)` must return one identity; its `NameTable` text must equal the `Assign.name`; and the variable must be in the already-visible `declared` set. A missing/split identity is a refusal.
- Its existing declaration placement must be complete and visible from the outer loop path. If the candidate needs to re-check the declaration row, use the placement's exact owner and anchor/type plus the emitted blank declaration, not a same-name search alone. For this fixture, the pinned Jarde text already shows the blank `String s1;` before the outer while, but the diagnostic did not observe the placement record for `s1`; bind it through the real same-run planner before accepting.
- The inline cast's semantic/reference type must agree with the target local's declared type. The fixed bytecode casts to `java/lang/String`, and the output declares `String s1`. The current inline-cast branch checks `CheckCast` and single consumers but does not itself compare the cast type with the binding target type. For an assignment branch, that equality/assignment-compatibility is a missing fact worth making explicit.

These are target identity and typing checks, not a demand to re-prove every later use. If the assignment node and declaration remain unchanged, later `s1.equals`, `s1.length`, `l2.add(s1)`, and the existing mutation order remain as built. The classfile shows those reads in the same body after BCI 25 and no other write to slot 4 in this method. That is useful fixed-input corroboration, but the smallest implementation should preserve those nodes, not rely on the current use list to erase them.

## Removal boundary and behavioral guard

Only the outer iterator's exact active-list declaration row and its `iterator()` initialization are returned in the current `remove` list (`build.rs:21941`–`:21950`) and later removed from the enclosing `self.stmts` (`:19264`–`:19270`). The `s1` declaration is not part of that list; the body-first assignment is a member of the detached loop body and should not be deleted. The existing local-owner helper already distinguishes a declaration row present in the active list from a cross-list elevated owner (`build.rs:11854`–`:11989`); that iterator-local deletion logic remains limited to local 3.

This keeps the iteration's observable operations ordered: enhanced-for still obtains `l1`'s iterator and performs `hasNext`/`next`; the retained cast still throws at the same body step; the retained assignment still occurs before the inner loop; the existing body still mutates `l2` and `l1` in its original order. Any shortcut that emits `for (String s1 : l1)` and deletes the assignment/declaration is a larger proof: it must show all reads/writes at every BCI belong to the same split-aware local, that no read escapes the proposed binding scope, that every later overwrite and branch remains equivalent, and that deleting the declaration is tied to its real owner/list. None of that is needed for the narrow body-assignment projection, so it should not be included.

The following forms should remain refusals unless separately proved: assignment to a different/split slot than the AST name suggests; compound/local-expression/field/index assignments; a RHS that is not exactly `next()` or an accepted inline cast of it; a `next()` value with multiple consumers or a cast result consumed somewhere other than the exact target store; uncertain target declaration/type/owner; iterator local changes, non-trivial iterator Phi arms, extra writes, intervening header effects, or different exception-handler coverage. In particular, accepting any `Assign` as the body prefix would only move the current first refusal and could synthesize a foreach around a side effect unrelated to `next()`.

## Conclusion and evidence boundary

The existing iterator proof, cast/next single-consumer proof, and parent-list deletion boundary are reusable. The smallest safe assignment-first extension for this fixed outer case is to admit only a simple, exact-origin local assignment whose RHS is the proven inline cast of that iterator's `next()`, cross-check the target slot/name/visible declaration/type through the existing planner and reuse identity, and retain the assignment and cast in the body while replacing only the call result with the synthetic foreach element.

Actual evidence proves only the early refusal at BCI 13 and the original class/source shape. It does not prove that the outer LocalVariable/placement gate, iterator Phi/readers, handler gate, or a candidate with assignment-first handling would pass. It also does not change the separate `ordinary_generic_source_unproved` report for `test`; generic signature projection remains an independent unresolved baseline behavior.
