# `lastIndexOf` latch provenance: read-only architecture audit

This is source-level analysis only. I did not run Cargo, JDK, JADX, the CLI, or Git, and I did not inspect or assume a runtime Region result for frozen CF07. In particular, whether its recovered loop body ends in a `Region::If` with one return arm and one direct `Straight` latch arm remains unproved until the private diagnostic is run.

## Existing certificate and the shape boundary

`Walker::implicit_tail_latch_origin` is deliberately narrow in `crates/jarde-java/src/region.rs:10279-10372`. It accepts only the last direct child of a loop body when that child is `Region::Straight`; its candidate is the last canonical block in that run (`10288-10295`). It then requires a natural loop at the exact supplied header, a unique non-irreducible natural-loop latch set containing the candidate (`10329-10340`), a terminal `goto`/`goto_w` represented as `Operation::Transfer`, and a normal-flow successor equal to that exact header (`10342-10350`). Finally it scans the complete canonical edge list and requires the candidate's only outgoing edge to be one Normal edge to that header (`10352-10370`). That last check rejects exceptional and extra canonical outgoing edges.

This certificate does not recursively search nested regions, and should not be generalized into such a search. A bounded extension could inspect only a final direct `Region::If`, then only a direct arm shape specifically stated by an accepted source-level case. If the diagnostic finds a `Sequence`, nested loop, fallback, or another structure between the loop body's final child and the physical latch, the source evidence does not authorize broad recursive latch discovery.

The existing `loop_region` path computes one natural-loop body, creates a loop-body frame, recovers its body, verifies coverage, and only then adds the inferred latch BCI to `gateway_origins` (`region.rs:10518-10557`, `10580-10625`; the latter lines are where the function closes and installs the `Region::Loop`). The same tail helper is also called by the header-test-chain path (`10375-10450`). An extension at that helper would therefore affect both callers unless scoped by an additional shape argument or caller policy. That coupling is a design constraint, not evidence that both paths should change.

## What ownership already proves

`Region::Loop` stores its physical body and its non-owning `gateway_origins` (`region.rs:512-535`). `Region::blocks()` lists header/tests and recursively lists body owners while intentionally preserving duplicates (`region.rs:712-729`, `814-845`). A `Region::If` owns its prefix, branch, and both arm blocks (`717-729`); `LoopContinue` owns no physical block (`847-849`). This means an origin for a goto already owned by an If arm can be added to the enclosing loop statement without creating another owner. The method-level completed-tree invariant can continue to catch any duplicate or missing ownership; a new ownership table is not indicated by these types.

`loop_arm_join_source` is an example of a completed-tree proof that composes existing facts rather than inventing another graph representation (`region.rs:4071-4187`). It checks the arm's declared exit against the requested join; requires a closed, structured body; compares unique Region owners with the exact natural-loop block set; checks path, visited/scope membership; limits accepted gateway origins; and scans all canonical edges incident on the loop owners to verify one exact entry and exits only to the join, rejecting non-Normal edges (`4104-4145`, `4148-4187`). It is specific to a loop used as a branch arm and is not itself a direct implementation for the last-If case, but its completed-tree ownership discipline is reusable as a model.

## Return arm and opposite latch arm

The generic If recovery already has a bounded allowance for an arm that leaves by a proved loop jump while the other reaches the join (`region.rs:3820-3898`). It distinguishes terminal `LoopBreak`/`LoopContinue` arms and, in a narrow case, a one-block transfer bridge to the loop's exact continue target. It does not define “return arm plus latch hidden inside the other arm” as a loop latch certificate. Whether CF07's `If` has a join at all, and which exact arm owns BCI 25, must come from the actual recovered Region.

If the diagnostic confirms a final direct If, the minimal safe proof boundary to consider is: select exactly the arm whose final direct child is a `Straight` run and whose last block contains the candidate transfer; establish from the other arm's actual Region and SSA that it exits the method by a return; and subject the selected transfer to the existing exact-header, unique-latch, terminal-opcode, normal-flow-successor, and full-canonical-outgoing-edge checks. Require the enclosing loop's own header identity, and reject `Fallback`, `Sequence` with unexpected children, nested `Loop`, multiple candidate latches, irreducible loop, or any candidate whose block is outside the loop's ownership/scope. This is a candidate proof contract for review, not a claim that the current CF07 tree meets it.

The unique natural latch requirement is important for inner loops: the candidate must be a member of the natural loop entered at the current loop header, and the entire latch set for that exact loop must contain exactly that candidate. Looking up the enclosing frame's last loop target alone is not enough to distinguish an inner loop's latch. The existing `loop_entered_at(header_node)` plus exact `natural_loop.header()`, `is_irreducible()`, `latches().len()`, and membership checks already state those facts (`region.rs:10297-10300`, `10329-10340`). A nested loop at the tail should remain rejected unless a separate explicit source shape is specified.

## Canonical edges, exception handling, and refusals

`NormalFlow::successors` is the projected normal-flow view (`crates/jarde-java/src/normal_flow.rs:257-275`); a check against it cannot by itself reject exceptional edges. The current helper's subsequent scan over `CanonicalGraph::edges()` supplies the complete outgoing-edge check and verifies kind and exact target (`region.rs:10352-10370`). Any candidate extraction around an If should preserve that full-edge verification; a may-throw instruction in the candidate latch block, a handler edge, or an extra normal edge must make the certificate return no origin.

The ordinary loop body frame is built in `Frame::loop_body` and resets `own_try` to `None` (`region.rs:2027-2081`, especially `2041-2063`). An If arm preserves the current `own_try` so catches can be matched (`2084-2114`). Thus an outer Try's ownership is not automatically retained across an ordinary loop-body frame. This is a separate observed source-level limitation from the latch-origin question. If CF07 or a follow-up case involves an exception-protected loop body, the candidate proof must use actual recovered exception/fallback evidence and must not infer that the loop-arm path is protected merely because an outer Try exists. A fallback arm is not a structured return arm: `Region::is_structured` is false for `Fallback` (`875-905`).

## Builder integration and atomicity

The current builder adds a derived terminal-goto origin to a nonempty If when `nonempty_if_join_transfer` proves that arm's transfer reaches the If's exact join (`build.rs:17551-17583`). The loop builder separately folds `gateway_origins` into the loop statement origin (`build.rs:17880-17889`, `18107-18144`). A loop-latch transfer targets the loop header, not the If's join, so it must not be forced through the If-join helper or added as an If's derived origin. The existing owner suitable for this hidden latch source is the enclosing loop statement, if and only if loop recovery certifies the full shape. This preserves the prior If join behavior and limits the builder edit to the loop-origin path.

The loop is only constructed after body recovery and coverage (`region.rs:10544-10625`); `StopReason` propagates through `Result` on helper calls. Any new candidate/edge iteration should charge `AnalysisSteps` before the scan and poll as it walks, following the current latch helper (`10329-10360`) and shared charge/poll contract (`crates/jarde-java/src/stop.rs:111-150`). It should return `Ok(None)` for an unproved shape and propagate `Err(StopReason)` unchanged. It must not mutate `gateway_origins` or publish source provenance until all proof checks pass; the existing local `gateway_origins` vector is assembled after body coverage, before the `Region::Loop` is returned (`region.rs:10580-10625`).

The existing helper charges the natural-latch count and then the canonical edge-list length. That gives a simple bounded pattern to retain. Avoid an uncharged recursive walk through arbitrary nested Region nodes or repeated whole-graph ownership scans. If a narrow arm inspection needs to visit a small number of direct Region children, charge/poll that work explicitly before examining candidates; the actual full canonical edge scan remains one charged pass for each proof attempt.

## Current evidence boundary

The frozen CF07 bytecode fact from the task context places the loop header at BCI 5, the return at BCI 21, the decrement at BCI 22, and the back-edge transfer at BCI 25. That establishes where to ask the diagnostic questions, not how the region layer recovers them. The private diagnostic must establish the real loop header and body tail, actual If join/arm variants, BCI 25's canonical block and complete outgoing edges, natural-loop latch set, and physical owner count before any production shape extension is proposed. No lastIndexOf runtime result or implementation change is asserted here.

There is a separate counted-loop presentation gap. `prove_for_header` requires the preheader's final two SSA instructions to be an integer constant `Push` followed by the induction-local `Store` (`region.rs:11155-11178`). CF07's known initial value is computed from the method argument (`end - 1`), so it does not satisfy that constant-push shape. Therefore the expected absence of a `ForHeader` is explained by the preheader proof boundary; that is distinct from whether BCI 25 can be derived as part of the recovered loop's origin. This audit does not propose widening `ForHeader` to solve the source-origin gap.
