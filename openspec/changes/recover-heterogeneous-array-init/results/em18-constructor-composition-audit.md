## Finding

The baseline fresh-object cases are stopped at two independent proof boundaries. The new-site rule does not count `aastore` as a consumer that writes the new expression. Separately, the initializer proof's expression collector has no atomic “verified construction” case, so merely changing that consumer predicate would still leave the array initializer unproved. This is a proof-composition gap, not evidence that the subtype assignment is invalid.

A narrow composition can fit inside the existing `ArrayInitializers` and `Sites` plans without a third pass or a new AST node. It must make both existing proofs agree on the same physical element/store/site tuple. A predicate-only change to `renders_its_reads`, or adding `Operation::Allocate` to the generic expression whitelist, is not safe: either would let `new@1` lean on an unproved array store, or let the initializer absorb a constructor run whose instance identity, single consumer, argument effects, or handler coverage was never proved.

The smallest safe seam is a narrowly scoped construction-as-element proof used only while proving an initializer candidate. It must reuse the existing `init::verify` evidence (allocation, `dup`, matching `<init>`, argument order/effects, and sole reader), with the exact terminal `aastore` as its required consumer. The array proof then accepts that construction as one bounded element expression only when the stored SSA value is the verified site instance and the complete initializer chain commits. `init::sites` should publish that site only against the committed initializer/store evidence. Keep the existing reference compatibility verdict in `Builder::array_initializer_element`; do not infer assignability from the `aastore` opcode or from the allocation's runtime behavior. This is an internal handshake between existing proofs, not a general array/object alias analysis.

The current top-level order is `ArrayInitializers::prove` followed by `init::sites` in `report.rs`. The handshake must account for that order (or revise the existing proof orchestration as one coordinated plan); independently moving all new-site verification earlier would regress the existing use of proved inline arrays in constructor arguments. The important invariant is atomic acceptance: neither plan should retain a half-proof if the other side rejects.

## Current proof boundaries

- `crates/jarde-java/src/report.rs:9374-9390` proves arrays first, then calls `init::sites` with the completed array plan. This order is intentional for constructor arguments: `init::verify` reads `inline_char_argument_bcis` and `inline_argument_chain_bcis` from that plan (`init.rs:629-668`).
- `crates/jarde-java/src/init.rs:435` is the `new@1` candidate verifier. It proves the adjacent allocation/`dup`, matching constructor, argument values produced within the expression, dependency/effect ordering, and one physical reader (`init.rs:455-460, 600-737, 739-807`).
- `outside_readers` counts reads of the site's produced instance (`init.rs:1641-1655`). `renders_its_reads` admits ordinary stores, calls, returns, control/arithmetic consumers, and claimed fields, but not array stores (`init.rs:1658-1684`). Thus a sole `aastore` is reported as a reader “this build quotes”; it does not reach element compatibility.
- `ArrayInitializers::prove` tries each `NewArray` candidate from the same block (`build.rs:12663-12720`); `prove_array_initializer` closes constant length, exact `dup`/constant index/store sequence, SSA single-use links, component/opcode agreement, a sole final consumer, and matching handler coverage (`build.rs:12792-13131`).
- For a non-array child element, the current proof calls `collect_expression_bcis` on the stored value (`build.rs:12891 onward`). Its admitted producers include calls and `NewArray`, but not `Operation::Allocate` (`build.rs:14232-14300`). Consequently, a fresh object construction is not currently an initializer element expression. The collector's interval and `dependency_uses_stay_within` checks are valuable closure safeguards; a broad whitelist edit would weaken them.
- Once plans exist, `Builder::render_value` maps the value of a verified site through `Sites::site_of` to `new_expr` (`build.rs:24150-24153, 25762-25888`). Array rendering already iterates the paired `(ValueId, store_bci)` elements and routes each through `array_initializer_element` (`build.rs:24828-24865, 26193-26255`). This is the existing rendering route a composed proof should feed.
- The element/store pair is the provenance used for compatibility. The current checker accepts null, exact component types, `Object`, and bounded hierarchy evidence via `initializer_reference_widens`; a missing proof remains a refusal (`build.rs:26229-26255`). It should continue to own the legal `CharSequence`, `Collection`, `Throwable`, and same-input-jar base/subclass decisions.
- `ArrayInitializer` already records `elements: Vec<(ValueId, u32)>`, `sources`, `owned`, `consumer`, and nested array `children` (`build.rs:12532-12561`). No new AST representation is required: the AST already has `ExprKind::New` as the rendered element and `NewArray { initializers }` as the enclosing expression.

## Invariants for the composition

The construction proof must establish that the exact stored value is the completed instance of that site, the site's complete `outside_readers` set is exactly the paired `aastore`, and there is no alias, extra call/store, `pop`, or second read. The initializer proof must still own the array allocation and its `dup`/index/store scaffolding, while the site owns its allocation/copy/constructor. Their evidence may overlap as expression provenance, but their statement ownership must not compete for a BCI or duplicate a source-map segment.

All value-producing operations in the array element must remain a closed, ordered interval ending at the paired store. Preserve existing side-effect checks: an invocation is admissible only when the construction verifier proves it is a constructor argument dependency and the initializer interval contains it once in physical order. Preserve every single-use edge around the array copy, index, element value, and construction instance. Compare ordered exception-handler coverage for the construction and its sole `aastore` consumer under the construction's existing handler rule, as well as the full initializer's allocation/store handler rule. A handler boundary must keep the composition refused.

Do not let a child construction become an independently committed initializer element if the enclosing candidate fails. On any failed side of the handshake, the current quote/refusal behavior must still account for all original BCIs without presenting a partial initializer or a dangling `new` record.

## Adversarial test matrix

Positive cases should put heterogeneous fresh values directly in one fresh reference array and verify the recovered expression, order, and source-map coverage: `CharSequence[] { "x", new StringBuilder() }`; `Collection[] { new ArrayList<>(), new HashSet<>() }`; `Throwable[] { new IllegalStateException(), new IllegalArgumentException() }`; and the same-input-jar `Base[] { new DerivedA(), new DerivedB() }`. Include constructor arguments with observable calls and distinguishable effects so each runs once in original array-index order. Compare original, JADX, and recovered behavior, and check one presented site per element plus one initializer.

Negative controls should retain refusal for: a nonconstant or out-of-order index; a second consumer or duplicated alias of a constructed value; a store to an array not proven by the initializer candidate; a construction crossing a block or handler boundary; an unrelated invocation/effect between `new`/`dup` and `<init>`; a value whose constructor result is not the `aastore` value operand; a failed/unknown component-assignability proof such as `new Object()` in `String[]`; and a partially built initializer whose later element fails. Include nested/empty arrays and existing varargs-array constructor arguments as regression controls for the shared plan order.

## Separate surrounding-main refusals

The baseline's `arraylength` inside a string-concatenation chain and omitted `System.out` field writes are independent losses in the surrounding main method. Do not attribute them to `new@1` rejecting an `aastore`, do not widen this composition to concat or array-length recovery, and do not use main-method output loss as a constructor-composition success criterion. The cleanest evidence remains isolated methods whose returned/assigned value is the initializer, plus the explicit element-site and source-map records.
