# EM18 saved-baseline refusal and stream analysis

This analysis reads only the saved patrol artifacts under `/private/tmp/jarde-em18-baseline-20261009`. Original reports, generated source, bytecode listings, javac errors and streams remain untouched. The same refusal sites and BCIs occur under Corretto 8 and OpenJDK 23.

For a direct array initializer, the saved bytecode shows `anewarray; dup; index; value; aastore` for each element, then stores or uses the completed array. That is a fresh stack-built initializer candidate: the array does not escape before its element stores. It is still necessary to prove each element assignment to the component type. The EM18-specific cases below explicitly refuse that compatibility proof. For arrays whose elements are freshly constructed objects, the raw allocation/store sequence is also direct and the hierarchy assignments are legal, but the CLI fails earlier while associating a `new` result with its only `aastore` use. Those results are therefore not clean evidence of an initializer-assignability rejection. StringBuilder concatenation around `arraylength` and omitted `System.out` field writes are separate losses in the surrounding main method.

## Per-family findings

- **Legacy CT, fresh source and frozen class:** the first substantive target refusal is `cov()Ljava/lang/Number;`, at the report marker BCI 23, after the fresh varargs array has been filled. Raw javap shows the two actual `aastore` instructions at BCIs 10 and 19 (the first follows `Integer.valueOf` at 7–10); BCI 23 is the subsequent local store. The report says the element is `Integer`, the component is `Number`, and no hierarchy fact proves the assignment. The fresh varargs `Number[]` then feeds `Arrays.asList` and local 0; because that write is refused, the later read at BCI 34 is also unbound. Generated source compilation consequently fails with “missing return statement” at `CT.java:48`; this is fallout from the refused non-void body. The other CT methods (`io`, `io2`, homogeneous `up`, `prim`, and `main`) are presented. The byte-identical frozen `CT.class` (SHA-256 `ed06cfab1a1a6c94b5b2d7677b802674529aa8b48d2df5bfdffffdcbc696e366`) reproduces the same refusal under both JDK runtime legs.
- **boxed-number-six:** the explicit marker refuses an inline `Integer` element into `Number[]` at BCI 53. The source has no `Number`-typed element local: all six wrapper expressions flow directly through `aastore` into a fresh `Number[]`. This is direct EM18 initializer-assignability evidence. The generated `main` compiles and exits 0 only because it contains no recovered computation; its stdout is empty, while original/JADX print `6:1:6`. Separate warnings report an interleaved `arraylength` in string concatenation and an omitted `System.out` field operation.
- **string-builder-charsequence:** bytecode directly allocates `CharSequence[]` at BCI 1 and stores a String at BCI 8 plus a freshly constructed StringBuilder at BCI 20. Both are legal CharSequence values. The report first says the array value is not read in a recovered body; it then refuses the `StringBuilder` new-site at BCI 11 because its only read is the quoted `aastore` at BCI 20. It never reports a component-compatibility verdict, so this is primarily the surrounding new-site/array-store composition gap, not a clean EM18 assignment test. Separate StringBuilder concatenation and `arraylength` interleaving warnings also occur. The generated source contains `jarde_refused_body()` and fails javac at `Main.java:35`.
- **arraylist-hashset-collection:** bytecode directly allocates `Collection[]` at BCI 1; new ArrayList is stored at BCI 13 and new HashSet at BCI 23. Both concrete classes implement Collection, and the fresh array/store sequence is visible. The new-site logic refuses each object because its only read is that array store; no component-assignment check is reached. Concat and `System.out` are additionally incomplete. Javac fails on `jarde_refused_body()` at `Main.java:39`.
- **exceptions-throwable:** bytecode directly allocates `Throwable[]` at BCI 1; freshly constructed IllegalStateException and IllegalArgumentException values are stored at BCI 15 and 27. Both are Throwable subtypes. As with Collection, the new-site logic refuses the fresh objects at their sole array-store uses before it can judge the component assignment. The concat chain and `System.out` are separate losses. Javac fails on `jarde_refused_body()` at `Main.java:39`.
- **nested-number-array:** the method first builds an `Integer[]` in local 1 and a `Long[]` in local 2. It then allocates a fresh `Number[][]` at BCI 27 and stores those locals at BCIs 33 and 37. The explicit refusal at report marker BCI 38 (after the final actual outer `aastore` at BCI 37) compares `Integer[]` with component `Number[]`. There is no prior upcast to a `Number[]` local; the two locals retain their narrower static types. This is direct EM18 initializer-assignability evidence. Like boxed-number-six, the generated source compiles and exits 0 with empty stdout after refusing the outer initializer; original/JADX print `2:1:2`. Its concat and `System.out` warnings are independent.
- **same-jar-derived-base:** the input jar includes Main, Base, Named, DerivedA and DerivedB. Main directly allocates `Base[]` at BCI 1; it constructs and stores DerivedA at BCI 13 and DerivedB at BCI 23. The subtype facts are present in the same input jar, and the array build is a fresh direct store sequence. The report instead refuses each fresh object because its only read is the corresponding `aastore`; the array expression is then marked unused. It does not reach a distinct Base-assignability decision. Concat/field-emission losses are additional. Generated main fails javac on `jarde_refused_body()` at `Main.java:39`.
- **corrected legal BigDecimal outsider control:** the corrected source `Number[] values = { new BigDecimal("1.25") }` is legal and the original runs as `1:1.25`. The Jarde main is explanation-only; its report refuses the `new BigDecimal` value at BCI 6 because its only read is the `aastore` at BCI 15. No component-assignability judgement is evidenced. The generated source fails javac on `jarde_refused_body()` at `Main.java:31`. This is only a closed-set outsider probe; it is not evidence that the Java assignment is invalid.

### Why boxed-number-six and nested-number-array are not recovery passes

Their Jarde javac and `java -Xverify:all` exits are 0, but their generated `main` bodies omit the observable computation and the report retains an initializer-refusal marker. Boxed-number-six has no Number-typed local at all; every wrapper value is an inline element of `Number[]`. Nested-number-array has locals, but they are `Integer[]` and `Long[]`, not `Number[]`; the refused outer initializer loads those narrow locals directly. In both cases the saved Jarde runtime stdout is the empty-stream hash `e3b0c442…b855`, not the original output. Exit status here means only that fallback source compiled and ran, not that recovery preserved behavior.
