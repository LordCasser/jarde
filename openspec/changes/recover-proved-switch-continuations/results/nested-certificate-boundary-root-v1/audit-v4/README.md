## Candidate cardinality: corrected proof

The previous note's blanket claim that every other candidate root must reach the proposed join was wrong: `prove_switch_fallthroughs` accepts physical Return/Throw leaves, so an unrelated target arm may terminate. The conclusion that two candidates cannot both pass still follows, but from `has_arm_predecessor` plus complete incoming/ownership closure and the empty-fallthrough requirement.

For a successful candidate J, `switch_forward_join` first requires a non-dispatch predecessor for J. At the candidate proof's end, the full incoming rows to J must equal exactly dispatch plus `join_sources` (region.rs:14803-14839, 15474-15548). Every non-dispatch source in `join_sources` belongs to an owned closure rooted at some *other* dispatch target. Suppose K is a second direct-target candidate with a non-dispatch predecessor p.

In J's proof, K is an ordinary case entry because only J is removed from the target map. If p is owned by a closure rooted at L != K, that closure's path to p→K records a case exit to K; candidate mode rejects the resulting non-empty fallthrough at the final join check (`!fallthroughs.is_empty()`, 15534+). If p were owned by K's own closure, K's closure would have to leave K and return to it, which the DFS grey-node check rejects (15230+). Thus J cannot pass when K has an arm predecessor. The same reasoning with J/K exchanged rules out both passing. This argument permits terminal paths elsewhere; it does not assert every candidate root reaches the other join.

Therefore the multiple-success list state is unreachable under the current proof contract, with a source-level invariant argument; there is no need for a list-length mirror test or injectable candidate seam. The final unique-slice branch is still not dynamically executed with a multi-entry list. Zero-success remains an ordinary result. The pinned real `A-multiple-exit` test is useful lower-layer refusal evidence (`real_multiple_exit_class_refuses_conditional_switch_certificate`, region.rs:18735-18765) but does not invoke `switch_forward_join`; do not call it direct enum-line coverage.
