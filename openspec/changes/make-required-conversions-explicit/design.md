## Context

"值正确"由文本决定，而不是由构建期意图决定。今天 `concat_expr` 已经把 append 的参数类型保存下来，却只处理 boolean；于是 `append((int) c)`（`c` 为 `char`）被写成 `"" + arg0`，在 `c == 'A'` 时得到 `"A!"` 而原方法得到 `"65!"`——两边都能编译。

## Goals / Non-Goals

**Goals:** 表达式构建期决定类型；消费位置要求与表达式呈现类型不一致时写出显式转换；用执行对照验收。

**Non-Goals:** 不引入完整子类型/泛型系统；不改拒绝与 fallback 契约；不改变既有布尔上下文与拼接片段转换的决定。

## Decisions

### 1. 决定在构建期，打印器不补偿

每个表达式节点携带"它呈现为什么类型"；消费位置（append 参数、调用实参、返回、赋值、字段写入）声明它要求的类型。二者不一致时，构建期插入显式转换节点（`Cast`），打印器只按节点拼写。这样"文本恰好能编译"不再依赖打印器所在位置的巧合。

### 2. 第一批只做已证明需要的形状

先修 concat 接受范围：`append` 的 overload 参数类型已保存，缺的是把它与片段表达式的呈现类型对齐（窄化 `char → int`、`byte/short → int`、必要时 `int → long/float/double`）。随后把同一机制复用到调用实参、返回与赋值。每一步都必须有对应反例，不做"通用化后再找用例"。

### 3. 无法证明就拒绝

转换合法性超出既有证据（例如需要子类型判定、需要未知的运行时类型）时，按既有 refusal 契约拒绝该区域，保留 bytecode 与 origin；MUST NOT 选一个"大概能编译"的拼写。

### 4. 验收只认执行对照

四个平面全绿、`javac` 通过都不是证据。每个反例都要有原类与恢复文本在同一输入集合上的执行对照（harness 已有：`tests/p3_execution_comparison.rs`）。

## Risks / Trade-offs

- 插入显式转换会改变既有文本（例如 `"" + arg0` → `"" + (int) arg0`？只有类型确实不一致时才插入）→ 逐条核对受影响断言，区分"本次有意改变"与回归。
- 转换节点会增加 `NormalizationClones`/`IrItems` 计费 → 给出前后计数对照，不用计费下降当收益。

## Migration Plan

按 tasks 分两步：concat 反例与转换节点 → 复用到调用/返回/赋值；每一步保持 workspace 全绿并附执行对照。

## Open Questions

无；需要扩展的消费位置清单由第一步的失败用例枚举。
