# Returned int-array update adversarial audit, Luna v1

Scope: independent read-only review of `implementation-luna-v1.patch` against the frozen base source and its existing tests. No source, test, fixture, workflow, patch, or notes other than this audit were changed. No Cargo, Git, Java, rustfmt, decompiler, or Jarde command was run. Findings below are static; proposed negative inputs have not been created or executed.

## Definite walker omission

`report.rs::collect_array_return_anchors` has its own nested `visit` match at `crates/jarde-java/src/report.rs:8529-8610`. It visits `LocalAssign`'s value, `Index`'s array/index, and explicitly lists every leaf, with no wildcard. The v1 patch updates the separate `collect_expression_anchors` walker around line 8687, but does not add `ArrayAssign` to this earlier return-anchor walker. Once `ExprKind::ArrayAssign` is added, this is an exhaustive-match compile failure. The smallest fix is a sibling arm that calls `child!(target); child!(value);`, so returned array assignment targets and RHS contribute all source origins to the generic return-candidate closure.

## Ownership and stop behavior

The intended claim shape is coherent on inspection: `CompoundAssignments::prove` builds a returned entry only after `prove_array_update(..., Some(return_bci), ...)` succeeds, keeps the return BCI available as the only expression publication site, and `Builder::instruction` skips the claimed prefix/store BCIs. A typed-render refusal is supposed to fall back at that return with the update's producer BCIs, while a `StopReason` bubbles out instead of writing a completed statement. This is static reasoning only, not a verified stop test.

The returned proof does use the budgeted `single_use_at_with_budget` wrapper and the existing budgeted dependency/interval walkers; ordinary proof calls retain `single_use_at`. The new dependency set is nevertheless cloned into `ReturnedArrayUpdate`, extended into `returned_owned`, and converted into a `Vec` by `returned_array_quote` without a separate poll/charge at those copy sites. The dependency walks already meter their visited evidence, so this is not a proof-boundary bypass, but these are newly added collection work proportional to expression size and should be considered against the instruction that new growing loops use the existing budget. The public test lowers `AnalysisSteps` by one from the complete class-source usage; that does not establish that a stop lands inside the returned proof/render path, and the patch explicitly makes no checkpoint-pressure claim.

The v1 implementation also assumes a specific `stack_operands` slice order in new slot patterns. The helper sorts `Slot::Stack` ascending, so patterns like `[Stack(2), Stack(1), Stack(0)]` cannot match its returned slice. The coordinating root has already identified and is correcting this; it is not counted as a newly discovered issue here.

## Negative-boundary coverage still absent

The v1 tests retain meaningful existing adversaries: the `merged` row-Phi case stays refused and its direct/derived source origins remain asserted (`tests/p3_nested_int_array_compound_updates.rs:400-429`); `different` keeps separate reads/writes and must not become `+=` (`:481-492`). The typed controls add a stronger Java-type boundary: descriptor-only boolean index/RHS inputs must not become Java `+=`, while char index/RHS inputs are accepted. These address type-evidence confusion, including category-1 frame `Int` versus Java `boolean`.

There is no direct negative exercising the new exact sum/dup_x2 consumer closure. The positive fixture proves only the canonical happy path. A small valid-JVM mutation of the existing `scalar` method is a minimal public-input control: its recorded bytecode is `iadd` at BCI 5, `dup_x2` at 6, `iastore` at 7, `ireturn` at 8 (`returned-next-baseline-v1/streams/javac8-javap.stdout`, lines 96-109). Insert `dup; pop` immediately after `iadd`, updating the Code attribute length. The duplicate consumer preserves the int stack and method result, but the arithmetic value now has an additional copy consumer and is no longer adjacent to `dup_x2`; recovery must not publish the returned `+=`. A second variant can insert `dup; pop` after `iastore` and before `ireturn`: the returned `dup_x2` output then reaches `ireturn` through a second consumer, and the required store/return adjacency is false. Both variants can be kept as frozen class fixtures and referenced from the same structure test.

No standalone wrong-dup-copy or non-int-return input appears in the current tests. A verifier-valid non-int-return control can reuse the scalar method's stack dance and then append `i2l; lreturn`, with descriptor `([III)J`; it must remain outside the return-value `int[] +=` rule and must not claim that output as an int assignment result. This tests the method descriptor guard without creating a verifier-invalid `ireturn`/long-descriptor class. A wrong-identity copy cannot be produced by merely changing an SSA identity in a verifier-valid class: the verifier and decoder derive copy identity from the actual opcode. That case would need a focused IR-level proof test or a crafted classfile whose stack behavior is valid but whose row/index inputs come from different producers; the existing row-Phi refusal is the current public classfile adversary for that family, not a direct dupx-output permutation test.

## Summary for root

Before compilation, add the missing `ArrayAssign` arm in `collect_array_return_anchors`; the patch otherwise updates the main expression traversals found in the changed files. For task 2.2's direct adversarial claim, retain the merged/different and typed controls, but add at least one extra-consumer class variant (the two `dup; pop` mutations above are minimal and verifiable) if the frozen boundary suite is expected to prove unique-consumer rejection rather than relying only on static proof inspection. No new tests or mutation inputs were run in this audit.
