## Context

接收者的拼写今天由两条互不相关的规则决定，二者都没有"槽位 0 是接收者"这个事实：

| 位置 | 事实 | 后果 |
| --- | --- | --- |
| `crates/jarde-java/src/names.rs::{is_java_identifier, alias_for}` | `this` 在 `JAVA_KEYWORDS` 里；别名规则对关键字追加 `_` | `LocalVariableTable` 写着 `this` 的槽位 0 变成 `this_` |
| `crates/jarde-java/src/names.rs:457` | 参数槽位没有名字时写 `arg{slot}`；槽位 0 落在参数区间 | 无调试信息的类把接收者写成 `arg0` |
| `crates/jarde-java/src/build.rs` | 局部名表逐槽位解析，不区分"这个槽位是接收者" | 接收者与普通局部同规则 |

JVMS 4.10.1.9 把实例方法与构造器的槽位 0 定义为接收者（构造器中是尚未初始化的 `this`），因此这不是启发式判断，而是字节码事实。

## Goals / Non-Goals

**Goals:** 实例方法与构造器的接收者按身份写成 `this`；其它槽位与其它命名的行为一字不改；产物文本在受控执行对照下与原类一致。

**Non-Goals:** 推断性命名（`str`/`obj` 一类）、改参数/局部命名规则、改 receiver 表达式的分组与求值规则、改 refusal/fallback 契约、装配 import。

## Decisions

### 1. 接收者身份来自字节码，不来自调试名

一个方法的槽位 0 是接收者，当且仅当该方法非 `static`（`ACC_STATIC` 未置位）。这一判断只使用已经读到的成员声明事实，不需要新的读取，也不受 `LocalVariableTable` 有无或内容影响：调试表把槽位 0 命名成 `this`、`this$0`、`self` 或什么都不说，都不改变它是接收者。

### 2. 呈现为接收者形态，而不是一个叫 `this` 的局部

字段读取、方法调用、以自身为实参、`synchronized`/数组长度等所有位置都写 `this`。理由：`this` 是 Java 里该位置唯一的自然拼写，且它不可能与任何局部或参数名冲突（关键字不能被声明）。文本里 `this` 出现即引用当前实例——这正是槽位 0 的语义。

反例检查：构造器在 `super()` 之前读 `this.f` 会改变可观察行为的前提不成立——呈现层只在**字节码原本就在该位置读取该槽位**时写它；本 change 不移动、不复制任何读取。

### 3. 只替换接收者的拼写来源，其它命名规则保持

`names.rs` 的槽位命名规则继续服务其它槽位：参数用调试名或 `arg{slot}`，局部用调试名或 `local{slot}`，不可拼写名继续 `alias_for`。改变仅在于：当一个槽位是接收者时，命名不再走"调试名 → 关键字别名"这条路径，而是直接取接收者形态。

不引入"保留旧拼写"的开关：一个产物里同一个接收者不应有两种写法，测试也不应同时接受两者。

### 4. 受影响证据一次性重基线

变更会改变大量既有文本预期（`tests/fixtures/p3-*`、`p2-golden`、`p4-golden` 以及断言具体文本的测试）。它们属于**本次有意改变**：更新时必须逐项确认差异只发生在接收者位置，不得借机放宽断言或改写其它文本。区分方法：对每个受影响断言，用"把 diff 中的 `arg0`/`this_` 只在接收者位置替换回 `this`"的可逆检查判断差异是否同源。

替代方案与不采用的理由：只修 `this_` 一项（把关键字别名规则对 `this` 特判）会让无调试信息的类继续写 `arg0`，同一件事两种拼写；只修无表情形同样不完整。二者都留下"接收者的写取决于调试信息"的依赖，因此不取。

## Risks / Trade-offs

- 受影响断言面广 → 用可逆的差异检查与受控执行对照控制，不通过"整体重写 golden"完成。
- 与 `add-parallel-bulk-recovery` 的 `class-source` 产物同时进行 → 两条 change 都改文本输出；实施顺序上本 change 先落地（它更小，且 `class-source` 的装配只需透传文本），避免同时改同一批断言。
- 误把非接收者槽位写成 `this` → 需要反例测试：静态方法槽位 0 的读取仍按既有 `arg0` 规则拼写，合成测试固定这一点。

## Migration Plan

按 [tasks](tasks.md) 形成独立可 review 的提交：命名与身份判定（含反例测试）→ 文本与 golden 重基线 → 受控执行对照与全量门禁。不需要迁移脚本：产物文本不持久化，也没有下游把旧拼写当身份（身份是物理 locator，不是文本）。

无。唯一需要在实施时确认的是受影响 golden 的**精确清单**（由实施首步的失败测试枚举得出，不预先猜测）。
