Review date: 2026-10-18. Read-only review of the planning snapshot at main `b45167b72486e22f942985340792dd730b308c56`; no implementation, build, CLI, network, or Git mutation was run. The four plan files and inspected source are pinned in `pins.json`.

## Finding

I found no plan-level soundness blocker. The narrow design is consistent with the current Builder and does not broaden foreach eligibility: it treats declaration deletion as an optional postcondition after the existing candidate has succeeded, and retains both loop and declaration when proof is absent. The fixed upstream class is reachable by the proposed whole-variable gate in both debug and no-debug profiles.

For the fixed original receipt (`execution.json`, SHA `1fbc03d8…`), the `test` method's debug and no-debug Code bytes are identical. In both profiles the only physical slot-5 operations are `astore 5` at BCI 33 (the iterator init store) and `aload 5` at BCIs 35 and 45 (the hasNext/next receiver loads); no other slot-5 access appears. Thus a strict full-method census over decoded instruction starts, keyed by the exact `LocalVariable`, accepts this positive baseline. A non-protected loop's current SSA write scan already spans all SSA blocks; the explicit gap is the protected-loop arm, whose write scan is limited to `loop_owned_blocks` (build.rs 23538-23607). A physical census closes that gap without making the original loop newly admissible.

## Required implementation interpretation

- Make “physical method” concrete: walk the complete decoded `MethodCodeFacts.instructions`/`Operations::iter()` sequence, not just SSA blocks, reachable regions, or the protected-loop block set. `Operations::of` inserts one entry per decoded instruction (decode.rs 93-100); load, store, and increment carry a slot, and `Increment` is both a read and write (facts.rs 646-675). For every slot-bearing access, resolve `reuse.variable_at(slot, bci)`: `None` is incomplete evidence and refuses only deletion; another proven `LocalVariable(slot,index)` is distinct; the exact target permits only init-store@33 and the two proven loads. Do not silently skip a missing operation or an opcode whose local operand cannot be resolved. In particular, account for `iinc` and any legacy local-operand instruction (`ret`/subroutine-shaped bytecode) as an access or fail closed. This matters because `Operation::Other` does not itself expose a slot.
- The exact deletion target is already well-founded: `LocalVariable` is `(slot,index)`, and `reuse.variable_at` deliberately returns `None` outside a known split range while unsplit slots resolve to `whole(slot)` (names.rs 396-427; reuse.rs 85-101). Therefore no-debug slot reuse must conservatively retain the declaration when the planner cannot prove distinct variables; it must not infer identity from slot or printed name alone.
- Keep the new relation append-only/multiplicity-preserving and add it to `FinallyCheckpoint` clone/restore. Its current fields do not include such state (build.rs 10304-10332, 17479-17541). `CompoundIfCheckpoint` embeds the finally checkpoint, so it inherits the addition. Only append after the transformed `ForEach` is successfully pushed. `arm`/loop construction swaps the current `stmts` vector while ancestors remain on the stack (build.rs 20716-20725, 24878-24905); final-tree confirmation is needed even with checkpoints because later parent quote/fallback paths can discard a child without using those checkpoints.
- Treat the record as a candidate, not authority. At finalization, before returning `Program` (build.rs 9256-9268), prove the exact recorded test BCI names one actual `ForEach` node, and exactly one direct-origin, blank `Iterator` declaration at the recorded init-store anchor lies earlier in a real enclosing Java statement list. Require the declaration's planned `(LocalVariable, owner, anchor)` and the loop's direct/derived origins to agree. A path prefix or same BCI elsewhere is insufficient. The candidate origin currently starts at the test BCI and incorporates the init statement's BCIs as derived origins (build.rs 23693 onward); preserve the init-store origin on the loop before deleting the sole declaration origin.
- Perform no destructive edit until all pending relations for that method have passed matching, uniqueness and ownership checks. Precharge/poll every census and final-tree visit before mutation so a Stop cannot leave partial deletion. Each deleted statement reduces `Builder.statements` exactly once; do not use saturating subtraction to conceal a bookkeeping mismatch. Consumed budget is not refunded. Existing `push` charges one `IrItems` and increments the count (build.rs 32370-32380).

## Scope and adversarial boundaries

- A real class with a second physical read/write to the same planned `LocalVariable` should keep the declaration while preserving the already accepted foreach. A same-slot access that `reuse` proves is another split variable need not block. A split-range access that resolves to `None`, any unrepresented slot operand, an extra store/read, or an increment must block deletion. These are reachable class-bytecode cases or incomplete facts respectively; do not report them as a failed foreach candidate.
- A test that mutates only SSA facts while leaving the physical Code unchanged is an internal facts mutation, not evidence that such a Java class reaches the path. Still fail closed if the implementation's decoded-operation/SSA consistency is incomplete; do not let such a mutation authorize deletion.
- Same-BCI duplicate AST nodes, duplicate candidate records, wrong declaration type/value/anchor, a sibling branch, or a parent fallback must all retain the declaration. Exact actual AST ancestry and source-origin checks in design.md §Decisions 4 address these cases.
- The budget plan is directionally sufficient: reuse the current `StopReason` result and avoid a second transaction framework. The implementation must ensure the new scan, saved relation, uniqueness traversal and final deletion are all billed; current candidate work has one up-front AnalysisSteps charge (build.rs 23249-23270), so a new whole-method census cannot be hidden inside that old charge unless its full work is represented. Only positive exact deletion changes the statement counter.

No controls have been executed for this new change. The planned internal mutation and controls in tasks 1-2 remain necessary to establish refusal behavior and checkpoint/Stop handling; this memo does not claim tests or acceptance.
