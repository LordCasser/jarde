## Observed source and classfile facts

- `RawParam.put(RawParam receiver,Object value)` is static; slot 0 is a raw receiver parameter. `aload_0; aload_1; putfield value:Ljava/lang/Object;` at BCI 2. The field has descriptor Object and Signature `TT;`. CLI refuses field Signature at writer BCI 2 and emits Object. Candidate reflection is Object; original reflection is T. A counterfactual that changes only candidate field declaration back to T compiles/runs on both VMs: javac sees `receiver.value` as raw Object selection. This confirms field T may coexist with a raw source receiver.
- `StaticRawLocal.put(StaticRawLocal receiver,Object value)` is also static slot-0-parameter, not `this`; bytecode stores the raw formal in local 2, reloads it, then `putfield` at BCI 4. Jarde preserves `StaticRawLocal local2 = arg0; local2.value = arg1;`. Current CLI refuses field T; field-T counterfactual compiles/runs on both VMs because the selected receiver remains raw.
- `InstanceRawLocal.put(Object value)` stores `this` in local 2, reloads it, then writes at BCI 4. Jarde renders the write as `this.value = arg1`, collapsing the raw-typed local alias into parameterized `this`. Current CLI erases field to Object and compiles/runs. Changing only field back to T fails in both javacs: `Object cannot be converted to T` at `this.value = arg1`. Bytecode provenance that local 2 came from `this` is not enough to select a raw field type; the emitted receiver expression/type matters.
- `ThisReceiver.put(T value)` writes direct `this.value`; method Signature `(TT;)V` is actually projected and the field Signature `TT;` stays published. Reflection reports T for both field and argument. This is the existing positive path.
- `TypedReceiver.put(TypedReceiver<T> receiver,T value)` has a real classfile method Signature `(LTypedReceiver<TT;>;TT;)V`, but CLI refuses that method Signature (`ordinary_generic_source_unproved`) and emits raw `TypedReceiver,Object`. Its separate native `observe(TypedReceiver<T>)` has an actually published Signature. The write method's field is erased. A field-T counterfactual compiles/runs because the *emitted* put receiver is raw. Do not borrow the sibling native method's published generic parameter or the refused writer's classfile Signature as source facts.
- `ShadowMethodT.put` has a method `<T>` shadowing the class `<T>` and classfile Signature `<T:Object>(ShadowMethodT<TT;>,TT;)V`. The CLI refuses this method and the native shadowed method Signature; reflection sees distinct method type parameters in the original and no such parameters in candidate. Its receiver/header remains raw after refusal. A field-T-only counterfactual compiles/runs with that raw source selection, but does not preserve the method’s generic API; this is not evidence to expand shadow-binder recovery.

## Existing proof boundary and minimal recommendation

`SameClassFieldUse` currently holds caller, `PhysicalMethodId`, BCI/opcode, constant-pool owner/name/descriptor, read consumer verdict, RHS `write_source`, and `source_complete`; it has no receiver slot/value/source type. `SameClassFieldWriteSource::Parameter { method, slot }` only certifies the RHS. `field_write_source` in `src/facade.rs` requires unique SSA BCI mapping, a direct parameter load, the loaded SSA value to have exactly one use at this `putfield`, and that load to read the unchanged entry local at a physical parameter slot (computed with the method static flag). This is a useful closed RHS proof and should stay closed; it does not prove the receiver, all formal uses, or arbitrary body typing.

Minimal reusable receiver evidence is a closed receiver fact attached to the physical field-use site: distinguish receiver-from-this (instance local 0) from a parameter slot (including static slot 0), and only accept a parameter’s source type from the same-run method record whose Signature actually projected. Existing method publication is staged before field publication; `SameClassPublishedMethodParameters.generic_parameters` is present only for a successfully projected method, otherwise proof sees the descriptor. Therefore: actual published parameterized receiver -> use its published type argument for the selected field type; absent/refused Signature -> use emitted physical/raw descriptor type and select field erasure. Do not inspect or guess from a refused Signature, another method’s Signature, or an unread callee Signature. Never force receiver argument’s binder to equal the field’s class binder; class-vs-method shadow `T` has distinct scope.

For local aliases, require proof that the actual emitted receiver expression remains raw. The instance alias example shows why value-origin alone is insufficient when the renderer rewrites the expression to `this`. A first slice can reject nontrivial aliases; it need not add new IR/parser or general method-body typing.

Keep existing guards: require complete use inventory, unique physical own field name/binding, CP owner/name/descriptor agreement, instance `putfield` for this feature, no same-name sibling physical fields, and the existing all-read-consumers expressibility proof. Do not parse field Signature to establish field identity; resolve the physical declared field from the same class read and use its exact owner/name/descriptor/access flags. Only then use its Signature as the candidate selected type. Keep field publication downstream of settled method publication; a failed field candidate erases the field without invalidating method publication.

Risks/out-of-scope: RHS proof currently does not model primitive boxing/conversion or arbitrary call-produced values; those appear as unknown SSA sources and must stay refused. It proves one loaded RHS value’s sole use at that write, not arbitrary use of a formal through the whole method. A new body path must not infer safety from one field-write BCI while allowing other formal uses to change typing. Unknown call consumer/source facts must remain refusal boundaries. Static slot 0 is never the implicit receiver. Whole-body constructor/method generalization, new IR/parser, field-publication reverse dependencies, and same-name binder identity checks are unnecessary for the raw-selection capability.

## Shared-candidate consumer edge

The constructor work also touches this topic through shared `GenericConstructorCandidate` consumers: `generic_constructor_declaration` in `src/class_source.rs` consumes the candidate for method-header projection; anonymous-super forwarding in `src/facade.rs` consumes it as `proof`; static-member inference around `src/facade.rs:27147` accepts `generic_constructor.is_some()` after an independent exact three-instruction `aload_0; invokespecial Object.<init>; return` check. If a candidate is widened to permit field writes, give it an explicit body kind/field-write marker and keep the old constructor-header, anonymous forwarding, and empty static-member consumers gated to the old empty/forwarding form. The static-member path's independent instruction check protects its exact empty Object case today; the anonymous path additionally compares exact forwarded slots and rejects constructor initializers, but a widened candidate that preserves the same forwarded slots could still be mistaken for a body that can be hidden. A generic candidate must not imply that the body is hideable.
