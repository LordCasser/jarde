# Test11 irreducibility trace

The marker `the graph is not reducible over 2 block(s) [48, 58]` is emitted by `region::recover`, before `Walker` starts and before any guarded-region rule is examined. The path is `report::recover` → `NormalFlowView::build` → `region::recover` → `NormalFlowView::irreducible_blocks` → `FallbackReason::Irreducible::message`. In `report.rs`, the view is built at 4062 and `region::recover` is called at 4114. `region.rs` computes the verdict at 1186 and returns the whole-body quote at 1187–1196. The walk's shared-finally probe is later (`region.rs` 2311–2324), as is its ordinary guard examination (`region.rs` 2427–2445); neither runs for this method. FINALLY's proof candidates are reached from `guard::examine` at `guard.rs` 5783–5795.

The pinned `test(List)` bytecode has exception rows `[0,4) -> 38 any` and `[38,40) -> 38 any`. The canonical plain-transfer edges around the handler loop are `38 -> 48`, `48 -> 58`, `48 -> 76`, and `58 -> 48`. Thus the cyclic SCC is exactly `{48,58}` and has one physical outside entry, BCI 48 (from handler block 38). The exception edges are `0 -> 38` for row 0 and `38 -> 38` for row 1: row 0 is stated by the call at BCI 1; row 1 has no throwing instruction and is represented from its protected block by the declared range. They are excluded from `NormalFlowView`, as intended, so BCI 38 and its normal descendants are unreachable from node 0 in that projection.

`NormalFlowView::build` computes `simple_fast` dominators only from node 0 (`normal_flow.rs` 179–187). Petgraph returns dominators only for nodes reachable from that root, so the immediate dominators of the handler component's nodes are absent. Consequently `dominates(48,58)` is false (`normal_flow.rs` 279–292). `irreducible_blocks` correctly finds the SCC's one physical entry, then incorrectly applies that method-rooted dominance relation to it (`normal_flow.rs` 329–350), producing `[48,58]`. This confirms the README hypothesis: root-relative plain-transfer dominance misclassifies this exception-only handler loop. The underlying mistake is mixing SCC-local entry facts with a dominance forest that has no root for the handler component.

A minimal safe correction should make dominance used for SCC reducibility component-aware: for a cyclic SCC with exactly one physical outside entry, compute or establish dominance from that entry within the SCC; preserve refusal when there are multiple physical entries. Keep the proved `catch_joins` exclusion exact. Do not add exception edges to the shared plain-flow graph, since that would alter ordinary try/branch analyses. To let the region walker subsequently structure the loop, the same component-root fact must feed loop-header/natural-loop discovery; changing only the preflight would merely expose a later unsupported-loop fallback. Keep zero-entry closed SCCs conservative unless a separate reachability policy proves them irrelevant.

Guard cases for a future change: retain rejection for a cyclic SCC with two distinct outside entries (including in handler code); do not exempt a second exceptional or normal entry by BCI alone; preserve the existing exception-row ownership checks that create `catch_joins`; and verify ordinary entry-rooted loops and a genuinely irreducible multi-entry loop still receive their current verdicts. Test11 alone establishes this false positive and the required correction boundary, not that its FINALLY copy proof will succeed after the graph fix.
