# DT-31: enum-switch audit

This audit separates three shapes: ordinary Java 8 remap-array switches, multiple remap-array switch sites in one method, and JADX's direct `ordinal()` switch from Smali. Only the first two are the Java 8 comparison. The direct-ordinal case is isolated evidence and does not support a Java 8 source projection claim.

The fixed JADX checkout is `2fb1b16386941660fda07e9017285aec40fcb37f`. The Jarde CLI baseline is `/tmp/jarde-cli-dt25-accepted`, SHA-256 `7bd7ebe1fd0837cd8ca552380361c23a006d4bb3a7818ed21850c66f5e290678`. The exact input sources and generated complete JADX/Jarde source families are under this directory. `replay.py` assembles the Java 8 class family, asks the fixed JADX and Jarde tools for full source, compiles each family with `javac --release 8`, and runs the same source-only runner with `java -Xverify:all`. It also independently assembles the sparse direct-ordinal Smali input and checks the generated JADX Java source. The replay normalizes only the changing snapshot identifier embedded in a Jarde comment so independent runs produce stable source hashes; it does not change code. Source and input hashes plus outcomes are in `replay-baseline/summary.json`.

The positive assertions are concrete. For one remap-array site, Jarde's proof record says `projected=true`, resolves keys 1 and 2 from the helper's actual `<clinit>` stores to `ONE` and `TWO`, and emits `switch (arg0)` with those enum labels. The complete original, JADX and Jarde source families all compile and produce `1, 2, 0, null:NPE`. For two sites in one method, Jarde's report identifies the `Count` switch at BCI 10 and the `Animal` switch at BCI 51, with the exact refusal `the method has multiple enum switch sites and grouped AST projection is not available`. Its complete source retains both integer helper-table switches; original, JADX and Jarde all compile and produce `21, 12, 20, null-count:NPE, null-animal:NPE`. Thus this is a source-label coverage gap, not a semantic or compilation failure. `replay-baseline/double/enum-switch-proofs.json` freezes both refusals.

The small input models the fixed `TestSwitchOverEnum` and `TestSwitchOverEnum2` structures: one method with one enum selector and one method with two different enum selectors, including all enum values and null evaluation. The runner makes both null exception points observable. It does not model every case arm, multiple sites over the same enum table, switches nested under control-flow constructs, mixed switch expressions, or altered helper mappings; those are outside the positive assertion and should be separate evidence before expanding scope.

The independently assembled Smali method switches directly on `Count.ordinal()` with sparse keys 1 and 2. Fixed JADX emits `switch (value.ordinal())` with numeric cases 1 and 2, and that source compiles and runs with the same values. In `FixSwitchOverEnum.mapToCases`, `caseCount` is 2, while the key 2 attempts `casesMap[2]` in an array of length 2; the caught bounds exception returns `null`, so enum-label replacement is skipped. Since DEX switch keys are ordered and unique, any non-dense key set beginning at zero also has a largest key at least the number of keys and takes this fallback. The observed behavior is conservative refusal, not incorrect case-index/ordinal association. No JADX semantic defect was reproduced. This test does not claim runtime execution of the original DEX or exercise Java 21 class-file lowering.

The existing cross-class enum-map OpenSpec covers proving a single site's mapping and preserving table semantics. The new proposal at `openspec/changes/project-multiple-enum-switch-sites/` is limited to applying multiple already-proved projections to one same-run method AST atomically. It does not alter map proof, method-local recovery, Java 21 ordinal handling, or unknown-map policy. A one-site unproved candidate or stop must leave the entire method on its integer path.
