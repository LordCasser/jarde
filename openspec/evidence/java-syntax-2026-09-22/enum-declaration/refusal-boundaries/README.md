# JVM-valid enum states Java enum source cannot reproduce

This directory records two deliberately invalid-for-source but valid-for-the-JVM enum class states. They are refusal boundaries, never positive examples of recoverable enum source. `Measure.java` is the same small enum used by the sibling `user-static-boundary` audit; `BoundaryRunner.java` prints constant `name()`, `ordinal()`, `valueOf` outcomes, and the unchanged user field/method results. `run_audit.py` compiles the source with javac 23.0.1 (`--release 8 -g:none`), invokes `patch_variants.py`, then verifies the baseline and both variants with `java -Xverify:all`.

`patched-name-alias/Measure.class` changes the string constant used when `<clinit>` constructs the field named `LOW`. Its enum instance is still stored in `Measure.LOW`, but has the name `ALIAS`: `valueOf("LOW")` now throws `IllegalArgumentException`, and `valueOf("ALIAS")` returns that instance. `patched-ordinal-two/Measure.class` changes the constructor argument for `HIGH` from ordinal 1 to ordinal 2: `HIGH` remains the result of `valueOf("HIGH")`, but `HIGH.ordinal()` is 2, with no enum at ordinal 1. The exact runtime observations are in `run-name-alias.txt` and `run-ordinal-two.txt`.

The patches do not change the field or method tables. `patch_variants.py` asserts this after each edit, and `patch-manifest.json` records each exact operation and digest. The name patch adds one `CONSTANT_Utf8` entry and retargets only the corresponding `CONSTANT_String`; the existing UTF-8 field name `LOW` and its field table entry stay unchanged. The ordinal patch changes one `<clinit>` opcode from `iconst_1` to `iconst_2`; Code length and tables stay unchanged. Both variants are class-file major version 52 and pass full JVM verification while retaining ordinary enum class/field/method flags.

These behaviors have no faithful Java enum spelling. Java source derives `name()` from the enum constant identifier and `ordinal()` from its position in the declaration. Writing `LOW` with a constructor name of `ALIAS`, or writing the second constant with ordinal 2, compiles to different runtime behavior. The preserved Jarde text and complete JSON reports (`jarde-name-alias.*`, `jarde-ordinal-two.*`) show why a source emitter needs an explicit refusal boundary when the class-file constructor values disagree with the names/order stated by enum fields. They are useful to prove a negative, not to justify inventing an ordinary `enum` source.

`javap-original.txt`, `javap-name-alias.txt`, and `javap-ordinal-two.txt` are full `javap -v -c -p` captures. `sha256.txt` freezes the original and patched class files. `jarde-cli-sha256.txt` records `/tmp/jarde-cli-static-root-after` at SHA-256 `8806d9aa06ad3b5fbcfe347144d09765dfbf3c9e172ee374eddf9313df893a44`. The Jarde CLI produced both source text and JSON with all evidence for each patched class; its stdout/stderr and exit statuses are kept beside them.

## Replay

Run `python3 run_audit.py` from this directory. The script is relative to its own location and was verified after copying the whole directory. It regenerates the original class, both patches, class hashes, `javap`, verified runner output, and Jarde reports. Set `JARDE_CLI` if the frozen CLI lives elsewhere. Required tools: Python 3, `javac`, `java`, `javap`, and the specified Jarde CLI. No Cargo command is used.

The root agent independently replayed a copy in `/tmp/jarde-enum-refusal-root-zLSNyl` on 2026-09-23. The original/patch class hashes, both verified runner outputs, and Jarde's name-alias text matched byte-for-byte.
