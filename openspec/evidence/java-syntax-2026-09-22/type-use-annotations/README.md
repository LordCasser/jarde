# Java 8 TYPE_USE annotation evidence

This fixture isolates runtime-retained, value-bearing `@Target(TYPE_USE)` uses on a field type, a method return type, and a method parameter type. `TypeUseRunner` reads each position through `Field.getAnnotatedType`, `Method.getAnnotatedReturnType`, and `Method.getAnnotatedParameterTypes`; an ordinary invocation is the behavior control. No declaration-annotation target is present on `TypeMark`.

Run `python3 openspec/evidence/java-syntax-2026-09-22/type-use-annotations/run_audit.py` to rebuild the fixture with `javac --release 8 -g:none`, save `javap -v -c -p`, run JADX 1.5.6, and call the frozen Jarde class-source CLI. The script verifies CLI SHA-256 `89b0d40ba45f69034d8e0ba0e9e22cfbea08655381ecd743b1f96e379f28d59a` and preserves every command's stdout, stderr, and exit status under `generated/`. It compiles the unedited source sets from original, JADX, and Jarde output independently; it runs each set with `java -Xverify:all` only after successful compilation.

Observed with javac 23.0.1 and Java 23.0.1:

| Complete source set | `javac` | Reflection output (field, return, parameter, behavior control) |
|---|---:|---|
| Original | 0 | `field`, `return`, `parameter`, `[o, k]` |
| JADX 1.5.6 | 0 | `null`, `null`, `null`, `[o, k]` |
| Frozen Jarde CLI complete set | 1 | Not run: the generated `TypeUseRunner` contains no recovered return for its private helper, and javac reports `missing return statement` |

To isolate the subject declaration from that unrelated runner-body failure, the script also recompiles Jarde's **unedited** `TypeUseSubject.java` alongside the original `TypeMark.java` and original `TypeUseRunner.java`. This isolated set compiles and verifies, and prints `null`, `null`, `null`, `[o, k]`. It directly demonstrates loss of all three annotations with the subject alone while preserving the ordinary behavior; it must not be confused with a successful compile or run of the complete Jarde output set. Its source list, status, and output are recorded as `jarde_subject_isolated` in `generated/summary.json`, with logs named `jarde-subject-isolated-*`.

`TypeUseSubject.class` is 429 bytes, SHA-256 `ca652feaf10023254cb32fef0e2ad07efebfb5ab97fc111bb192bc0b45c5619e`. Its `javap` output proves all three `RuntimeVisibleTypeAnnotations` entries and their exact target types: `FIELD`, `METHOD_RETURN`, and `METHOD_FORMAL_PARAMETER` with `param_index=0`. The original source and class hashes are in `generated/summary.json`. The JADX source compiles and verifies, but has no `@TypeMark` at any of the three positions: all three reflection checks become null while the ordinary behavior remains unchanged. That is silent type-annotation loss. Jarde also omits the three positions in `TypeUseSubject`; its complete generated set is not a successful execution result because javac fails first for the unrelated unrecovered helper body. The isolated comparison above confirms the Jarde subject's annotation loss independently. The script and logs intentionally preserve this distinction.

The Jarde JSON for `TypeUseSubject` reports empty class `annotation_attributes`, `annotation_uses`, and `annotation_refusals`; field/method declarations likewise contain no annotation-use data. Local architecture clues: the reader's release registry recognizes the `RuntimeVisibleTypeAnnotations` and `RuntimeInvisibleTypeAnnotations` attribute names, while class-source assembly currently selects only `RuntimeVisibleAnnotations` and `RuntimeInvisibleAnnotations` in [`src/facade.rs`](../../../../src/facade.rs). The nearby class/member annotation proposals explicitly list type-use as a non-goal. This evidence identifies the gap; it does not prescribe implementation structure.

Source-position limits are frozen separately in [`placement-boundaries/`](placement-boundaries/README.md) and [`primitive-boundaries/`](primitive-boundaries/README.md). Root replayed the former in an independent copied directory with byte-identical summary, and independently rebuilt the latter's baseline and type-only patch: both class SHA-256 values matched the recorded hashes, `java -Xverify:all` loaded the patch, all three declaration annotations were absent while all three primitive type annotations remained, and the three complete `Code` attribute hashes were unchanged. These boundaries justify the narrow qualified-reference scope in [`recover-qualified-type-use-annotations`](../../../changes/recover-qualified-type-use-annotations/design.md) without assuming an external annotation type's `@Target`.
