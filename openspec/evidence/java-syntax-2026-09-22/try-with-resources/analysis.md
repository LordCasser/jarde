# TWR boundary analysis

The successful core class shows that the existing TWR proof can reconstruct both a nullable factory result and a factory that throws during initialization. The source header for the latter is retained, while the runtime oracle observes one initializer call, zero completed opens, zero closes, and the same exception object at the caller. The multi-resource sample confirms runtime close order and suppressed-object identity: resources initialize 1, 2, 3; close runs 3, 2, 1; the primary remains the body exception and `getSuppressed()` contains the exact close exception objects in that order. Jarde's complete reconstructed classes compile and produce the same runner lines as the original classes and JADX.

The isolated null case is different. The source says `try (NullResourceCore resource = null)`, and the original class and JADX both compile and run: the body executes once and `close()` is never called. Its real bytecode stores `aconst_null` at BCIs 0–1, runs the body at 2–10, then has `ifnull` close guards and a `Throwable` suppression handler. `javap` shows the `close()` call targets `NullResourceCore.close()`. Jarde reports `jre_region_exception_edge` at BCI 0 and `jre_region_uncovered_blocks` for the remaining handler blocks; this method has no `twr` rule in its report. Its fallback text treats the null local as `Object`, writes the compiler's `Throwable` handler as a catch, and calls `local0.close()`. Whole-class `javac` rejects that method because `Object` has no `close()`; the audit records the error and skips runtime without changing the generated text.

The first observed refusal is at the guard/region boundary. `guard.rs::initialises_resource` recognizes a header store only when the statement contains `Allocate`, `Invoke`, or `InvokeDynamic` ([guard.rs:785](/Users/lordcasser/workspace/projects/jarde/crates/jarde-java/src/guard.rs:785)). The null initializer is only `aconst_null; astore`, so it is not admitted as a resource header. The region walk then cannot claim this `catch_type == 0` exception edge as a TWR or named catch and quotes it as `jre_region_exception_edge` ([region.rs:1260](/Users/lordcasser/workspace/projects/jarde/crates/jarde-java/src/region.rs:1260)). This matches the report: no TWR rule is attached to the region, and the synthetic cleanup escapes into fallback output.

There is a separate source-value constraint after guard proof. `build.rs::resource_declaration` derives the declaration type from the stored SSA value and requires a reference type with a name other than `Object` ([build.rs:1764](/Users/lordcasser/workspace/projects/jarde/crates/jarde-java/src/build.rs:1764)). The current null case never reaches this function, so this audit does not claim it is the first failure. It is still a second boundary that must be accounted for before a null resource can be emitted as a typed header. The original `StackMapTable` names `NullResourceCore` for the local at the handler frames, but the Java frame pass explicitly does not read `StackMapTable` ([frame.rs:16](/Users/lordcasser/workspace/projects/jarde/crates/jarde-jvm/src/frame.rs:16)); that external `javap` fact is not currently available to `resource_declaration` as a proved type. The bytecode's proved normal close receiver also names the current class, and its header declares `AutoCloseable`, but this audit does not establish a safe general source of a resource's source type from arbitrary close owners.

The smallest architectural direction for a follow-up is therefore to examine the existing TWR proof and the resource declaration type as one bounded case: decide what existing bytecode facts are sufficient to admit an `aconst_null` initializer and emit a legal typed header, while keeping synthetic `Throwable` cleanup owned by TWR. Do not relax the generic region fallback into a user `catch`. Type recovery for external owners, interface selection, and accessibility remains unproven here and should stay outside that first case.

Existing evidence already covers the neighboring behavior and should not be duplicated: `tests/p3_guard.rs` checks one-, two-, and three-resource headers, reverse normal close order, suppression direction, missing exceptional close, and initialization-range refusal ([p3_guard.rs:259](/Users/lordcasser/workspace/projects/jarde/tests/p3_guard.rs:259), [p3_guard.rs:294](/Users/lordcasser/workspace/projects/jarde/tests/p3_guard.rs:294), [p3_guard.rs:451](/Users/lordcasser/workspace/projects/jarde/tests/p3_guard.rs:451), [p3_guard.rs:497](/Users/lordcasser/workspace/projects/jarde/tests/p3_guard.rs:497)). `tests/p3_twr_catch.rs` documents the unchecked close shape for a non-null `new` initializer, user-catch row partitioning, and the still-refused return tail ([p3_twr_catch.rs:15](/Users/lordcasser/workspace/projects/jarde/tests/p3_twr_catch.rs:15), [p3_twr_catch.rs:34](/Users/lordcasser/workspace/projects/jarde/tests/p3_twr_catch.rs:34)). Its user `catch` scenario is why this audit does not add another catch variant. The present OpenSpec also says TWR failures must not degrade into ordinary `catch`/`finally` ([java8-recovery spec:79](/Users/lordcasser/workspace/projects/jarde/openspec/changes/present-proved-java-structure/specs/java8-recovery/spec.md:79)).
