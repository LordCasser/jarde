# Findings

The source compiles with javac 23.0.1 targeting release 8 to a 1,346-byte class (`163282a201ca5c2cf7ae0485f92f472802c34d8bd2fe8367fff0ed1400f0f46d`). `javap.txt` confirms the compiler-generated protocol before either decompiler is assessed: a synthetic `static final boolean $assertionsDisabled`; `<clinit>` loads the `AssertProbe` class literal, calls `Class.desiredAssertionStatus()`, inverts the result through a branch, and stores it in that field. Each assert body first reads the field, skips the remaining work when assertions are disabled, evaluates the condition once, and only on false constructs `AssertionError(Object)` after evaluating the message expression.

The original complete class recompiles with the same runner. In a fresh `-ea` JVM, success evaluates the condition once and not the message; failure evaluates both once and reports `AssertionError` with `failure-message`; exceptions from the condition and message propagate as the exact supplied objects. In a separate `-da` JVM, all four assertion bodies return without evaluating either expression. The complete JADX source recompiles and produces byte-for-byte identical output to the original in both modes; see `original-ea.txt`, `original-da.txt`, `jadx-ea.txt`, `jadx-da.txt`, and the empty diffs.

The complete jarde source does not compile, so it has no runtime result. `jarde-javac.log` reports that `$assertionsDisabled` may not have been initialized. The unedited generated source declares this field `static final` but its `<clinit>` contains only refusal markers. The class initializer's first rejected producer is the `ldc` class literal at BCI 0; the following `desiredAssertionStatus()` call, conditional boolean merge, and `putstatic` at BCI 13 are consequently not recovered as an assignment. The four assertion methods themselves are emitted as nested `if` statements, condition calls, and `throw new AssertionError((Object) message(...))`; the javac diagnostic does not identify their syntax, branch, throw, or local-name presentation as the compile blocker.

This evidence points first to class-literal and static-initializer value recovery for javac's synthetic assertion flag, rather than a distinct assert-statement emitter defect. A focused follow-up could establish whether existing value and initializer support can represent `AssertProbe.class.desiredAssertionStatus()` and its branch-fed final-field store. Another possible route is class-wide recognition of this compiler protocol and reconstruction of source `assert` statements while omitting the synthetic field. Either route must prove the condition/message gating and all uses of the flag as a unit. No plan change is proposed from this probe alone.

Root replay after `recover-class-literals` is frozen in `root-after-class-25bf/` with CLI SHA-256 `25bf181ccf0d879351a16710818e27efba0df6b3851931a29eb98d9f41adb1e0`. The original 1,346-byte class and the two JVM modes are unchanged; JADX still compiles and matches both modes. Jarde now writes `AssertProbe.class.desiredAssertionStatus()` in `<clinit>` and reduces four quotes to one, but emits an empty `if` and quotes `putstatic Z` at BCI 13 because its input is the entry stack Phi. The unedited complete class still fails `javac` on uninitialized `$assertionsDisabled`, so no jarde runtime is claimed. The remaining bounded work is a proved two-arm conditional value at a field consumer, recorded in the existing `recover-conditional-values` OpenSpec change; no assert-specific statement mechanism is justified by this evidence yet.
