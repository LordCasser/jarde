# 合成名字与整类重编译边界

自写Java8类保留debug局部名`p0_`，同一方法包含两个捕获该局部的IntUnaryOperator。原class在`-Xverify:all`下输出22，JADX实际完整类重编译后同样输出22。当前jarde没有引用，但完整javac失败。

两个问题必须分开：

1. Builder先用NameTable.free_name取得`p0`，第二个lambda再因已有合成形参而自行追加下划线，却未重新检查原局部。因此输出`(int p0_) -> ... (p0_, p0_)`，既非法遮蔽局部，也把捕获参数误绑为lambda参数。非槽名字应每个候选同时检查NameTable与本次Builder已分配名字；这是后续保存值复用现有分配入口时必须守住的约束，不应另建互不知情的命名集合。
2. **仅作为方案实验**修正第二个形参和对应读取后，javac仍报告已有`lambda$repeated$0/1`方法与本次编译器生成的同名方法冲突。原方法头被忠实输出、lambda调用又重新触发编译器合成，整类层面还缺一致的表达策略。此问题涉及合成方法声明与引用，不能靠局部NameTable或文本替换修好，也不能把方法删掉后宣称完整类已恢复。应另案检查同类方法声明/调用与lambda实现体的所有权，再决定最小方案；本项尚无生产修改。

`hypothesis.java.txt`只验证第一问题被移除后第二问题真实存在，不能作为实际恢复成果。相邻的求值顺序修复可统一其必需的非槽分配入口，但不因此重写整个lambda成员呈现机制。原class/JADX/jarde、编译错误、候选实验和可重放脚本均保存在此目录。
