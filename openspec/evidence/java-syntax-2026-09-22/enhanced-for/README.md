# Java 8 enhanced-for source-only audit

This audit compiles three separate Java 8 class files for `for (int x : int[])`, `for (Object x : Object[])`, and `for (String x : Iterable<String>)`. Each runner checks empty and multiple values, null containers, source-expression calls, and observable exceptions. The iterable runner also counts `iterator()`, `hasNext()`, and `next()` at each exit. Source and runner files are kept beside the command outputs; `run_audit.py` can reproduce the complete audit.

The input compiler was `javac 23.0.1 --release 8 -g:none`; execution used `java -Xverify:all` on OpenJDK 23. The frozen CLI `/tmp/jarde-cli-boolean-root` had SHA-256 `8cd1f767ba8cde9928bacedc29263d44be8e5e61b46d3b6f00456fac1c7c77cd` both before and after replay (`cli-sha256-before.txt`, `cli-sha256-after.txt`). Exact CLI class-source stdout is retained in each case's `jarde.java.txt`; CLI diagnostics are in `jarde-report.txt`. Original class files, full `javap -v -c -p` output, JADX source, per-command stdout/stderr/status, runtime output, and line comparisons are also retained. The JSON inventory records each command and its exit status.

The two array loops are emitted as ordinary index-based `while` loops. Empty and three-element arrays agree on their values, and `Supplier.get()` is called once for both a successful source and one returning null or throwing. A null array produces `NullPointerException`; source exceptions preserve their type/message and one-call count. In the object-array body, `hashCode()` calls before/at a throwing element occur once and the following element is not visited. The exact row comparisons live in each case's `comparison-original-vs-jarde.txt` and `comparison-original-vs-jadx.txt`.

For `Iterable<String>`, the original and JADX executions agree on iteration counts and exception types across normal, empty, null, `iterator()`, `hasNext()`, and `next()` cases. The jarde source retains the pre-loop `iterator()` call, but refuses the loop at its condition: `loop@1` reports that the `hasNext()` invocation in the test block is not part of a value expression. That produces fallback-only loop bodies and javac's two missing-return errors. `2c.6` in `openspec/changes/present-proved-java-structure/tasks.md` is exactly this boundary: calls and field reads used by a loop condition may remain in the condition, with their per-test execution count; stores and `iinc` remain refused. The Java source does not prove or require an enhanced-for statement node.

JADX differs from the original on one of the ten iterable runner lines: the JDK 23 helpful-NPE text for a null element says the null came from `Iterator.next()` in JADX's inlined `it.next().length()` body, while the original says it was the temporary local. Both throw `NullPointerException` after one iterator, two `hasNext()`, and two `next()` calls. This is an exception-message attribution difference from JADX's source rewrite, not a difference in iterator effects or exception type; the exact text is retained in the line comparison.

An initial `Object[]` experiment with an `if (value != null)` nested in the loop body is preserved in `object-array-body-if-red/`. Its frozen jarde output emits the array local and length, then reports `jre_region_loop_shape` at the loop header (BCI 10; source-expression variant BCI 18), leaves two loop blocks as bytecode references, and fails whole-class javac at both method ends. The simpler straight-line `Object[]` case above compiles and executes fully. This RED is a loop-body region limitation already described by the existing loop-shape/fallback contract; it is not evidence for a new foreach construct.

## Reuse and scope

There is no new enhanced-for AST or control-flow mechanism indicated by these results. The current representation has `Region::Loop` with `LoopForm::While`/`DoWhile`, `StmtKind::While`/`DoWhile`, and reusable expression nodes for `array[index]`, `array.length`, ordinary casts, and calls. The array bytecode is a stored array reference, a fixed length, an index, an element read, and an increment; those facts already fit the existing array-expression and loop path. The generic iterable bytecode is an iterator local plus `hasNext()` condition, `next()` value, and a `checkcast` for the erased `String` element. It fits the existing local, call, condition, and cast path once the planned condition-value rule admits the call. Since hand-written iterator loops have the same bytecode shape, reconstructing `for-each` would claim source syntax that the class file does not prove.

The relevant existing work is `2b.1`/`2b.5` for array loads and array-element typing, pending `2b.6` for array values in loop tests, and pending `2c.6` for calls used by loop tests. The older baseline already records `for (int x : a)` as index-based `while` and `for (String s : list)` as the `hasNext()` condition boundary at `baseline-three-way.md:416-417`; the enum-array case at `1415-1417` records a complete loop-plus-call recovery as `while`, not a foreach guess. The extra nested-if RED belongs under existing loop-region proof (`region.rs`'s `header_tested_loop` body coverage and `LoopShape` refusal), separate from these expression cases. This audit found no additional OpenSpec task to propose.

The relevant implementation points are `crates/jarde-java/src/region.rs:2101-2133` (`test_is_pure`), `region.rs:2243-2360` (loop shape and body coverage), `crates/jarde-java/src/decode.rs:168-178,321-348,735-744` (array, length, and cast facts), `crates/jarde-java/src/ast.rs:174-192,238-260,590-593` (existing expressions and loop statements), and `crates/jarde-java/src/build.rs:1424-1457,4306-4340,4404-4479` (loop emission, casts, index reads, and length reads). No production or Rust files were edited for this audit.
