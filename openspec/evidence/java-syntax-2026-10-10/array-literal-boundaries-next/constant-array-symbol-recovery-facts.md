# Constant-to-symbol recovery: architecture facts

Read-only comparison of the local JADX dev checkout's array-literal path and Jarde's existing integer-constant projection. The executed baseline uses JADX 1.5.6; observed output agrees with these candidate seams, but the installed binary's internal call path has not been traced. The Atlas query against JADX reported a complete scope containing only one file, so the upstream facts below were confirmed by direct source reads; Jarde's scoped Atlas hits were also checked against the files.

## JADX: value table meets array construction

- [`CollectConstValues.java:27-63`](/Users/lordcasser/workspace/testzone/jadx/jadx-core/src/main/java/jadx/core/dex/visitors/prepare/CollectConstValues.java:27) registers only fields when replacement is enabled and the field is `static final`, has a non-null `ConstantValue`, and has no remaining bytecode uses. Thus a Java constant variable whose use the compiler inlined can be restored from the retained field declaration.
- [`ConstStorage.java:21-48,75-85`](/Users/lordcasser/workspace/testzone/jadx/jadx-core/src/main/java/jadx/core/dex/info/ConstStorage.java:21) stores candidates by value in either a public/global table or a class-local table. A second candidate with the same value removes the mapping and marks that value ambiguous; further duplicates stay unavailable. [`ConstStorage.java:96-133`](/Users/lordcasser/workspace/testzone/jadx/jadx-core/src/main/java/jadx/core/dex/info/ConstStorage.java:96) searches the current class and its lexical enclosing classes (`ClassInfo.getParentClass`, not the superclass chain), and only searches the public/global table when requested; a value also present globally suppresses a local match. This is value identity plus scope/uniqueness, not a bytecode edge tying a literal use to the source field.
- [`ConstStorage.java:160-191`](/Users/lordcasser/workspace/testzone/jadx/jadx-core/src/main/java/jadx/core/dex/info/ConstStorage.java:160) first uses the recovered primitive type, converts to its corresponding boxed value (`int` to `Integer`, `long` to `Long`, etc.), then applies per-type thresholds for searching public candidates (absolute literal magnitude: int `> 100`, long `> 1000`, byte/char `> 10`, short `> 100`; boolean never searches globally). This avoids looking up many small/common literals, but does not establish source-use identity.
- [`ModVisitor.java:124-135,561-595`](/Users/lordcasser/workspace/testzone/jadx/jadx-core/src/main/java/jadx/core/dex/visitors/ModVisitor.java:124) replaces a `NEW_ARRAY` followed by its first-use `FILL_ARRAY` when the sizes match. It converts payload values using the array element type, then asks the same constant table about each typed element and emits either an `SGET` field reference or the literal. This is a concrete typed array-literal lookup seam in the local checkout and a candidate explanation for the observed `TestArrayFillConstReplace` output, not a traced assertion about the installed 1.5.6 binary.
- [`InsnGen.java:657-680`](/Users/lordcasser/workspace/testzone/jadx/jadx-core/src/main/java/jadx/core/codegen/InsnGen.java:657) is the other path: an uncombined fill emits indexed stores from typed payload literals. `TestArrayFillNegative.java:11-17,23-28` deliberately uses dependent `arr[0]`/`arr[1]` reads and ordinary stores, so it is not an all-constant payload to fold.
- The observed [`TestArrayFillConstReplace.java:11-16,21-25`](/Users/lordcasser/workspace/testzone/jadx/jadx-core/src/test/java/jadx/tests/integration/arrays/TestArrayFillConstReplace.java:11) has a same-class `public static final int CONST_INT = 0xffff` and `new int[] {127,129,CONST_INT}`. Since javac stores the array element as an `int` value and inlines the constant-variable use, JADX can find the unique public/global `65535` candidate for that element. The equal value still does not prove the original source wrote `CONST_INT`; the source test provides that fact only for this fixture.
- `Long.MAX_VALUE` is a distinct path: [`StringUtils.java:473-494`](/Users/lordcasser/workspace/testzone/jadx/jadx-core/src/main/java/jadx/core/utils/StringUtils.java:473) spells the exact `int`/`long` extrema using standard wrapper names in `AUTO` format. That is a numeric formatting rule, not recovery of a field declared by the input class. An original numeric literal at the same value would receive the same spelling. `TestArrayFill4.java:13-18` also shows the unrelated size-field guard: its assertion forbids reconstructing `new long[ARRAY_SIZE]` while the array contents use the built-in `Long` extrema.

## Jarde: reusable expression node, narrower use-site proof

- [`src/facade.rs:7142-7194,7251-7292`](/Users/lordcasser/workspace/projects/jarde/src/facade.rs:7142) reads each field's `ConstantValue` once for its declaration. It creates a name candidate only for a spellable same-class field with `ACC_STATIC|ACC_FINAL`, descriptor `I`, exactly one `ConstantValue`, and a Java identifier. Incomplete field inventory clears candidates; duplicate field names and duplicate candidate `i32` values are rejected. The retained candidate records its physical `FieldItem`, name and exact `i32` value ([`src/class_source.rs:407-413`](/Users/lordcasser/workspace/projects/jarde/src/class_source.rs:407)).
- [`src/facade.rs:7561-7562`](/Users/lordcasser/workspace/projects/jarde/src/facade.rs:7561) captures method ASTs only when candidates exist. The post-pass runs only after complete execution and while member-family, nested-enum, nested-annotation and anonymous-interface projections are all absent ([`src/facade.rs:2170-2188`](/Users/lordcasser/workspace/projects/jarde/src/facade.rs:2170)). It further requires complete class/method execution, structured Java recovery with statements and no fallback, then derives a projection anchored to both the field identity and the use BCI ([`src/facade.rs:19181-19311`](/Users/lordcasser/workspace/projects/jarde/src/facade.rs:19181)).
- The existing expression node is reusable in principle: `ExprKind::IntegerConstantName` is an `int` expression and the emitter writes its stored name ([`crates/jarde-java/src/ast.rs:195`](/Users/lordcasser/workspace/projects/jarde/crates/jarde-java/src/ast.rs:195), [`crates/jarde-java/src/emit.rs:1179-1183`](/Users/lordcasser/workspace/projects/jarde/crates/jarde-java/src/emit.rs:1179)). But its current producer is intentionally narrower: [`crates/jarde-java/src/report.rs:3827-3835,3949-4000`](/Users/lordcasser/workspace/projects/jarde/crates/jarde-java/src/report.rs:3827) rewrites integer `switch` labels and a direct integer return in a selected switch arm. It does not walk array-creation element expressions. At the facade call, `returns_int` is based on a method descriptor ending in `)I` ([`src/facade.rs:19219-19224`](/Users/lordcasser/workspace/projects/jarde/src/facade.rs:19219)); an `int[]` return descriptor ends in `)[I`, so this route cannot admit an array-returning `test()` as the direct-return case. The confirmed empty `integer_constant_projections` for these array classes is therefore consistent with the present use-site scope, not missing field metadata alone.
- Candidate matching is still heuristic: it proposes a name for an equal `i32` in the admitted syntactic sites after requiring one unique same-class candidate. It cannot prove that source expression named that field; equal source constants and compiler-inlined references have the same classfile value. The current representation is only `i32`, so it does not cover the `long` extrema spellings that JADX's formatter supplies.

## Boundary

JADX already demonstrates that typed literal-to-field lookup can be placed at the filled-array element seam, with ambiguity suppression and visibility scopes. Jarde already has the named-`int` expression and candidate/provenance machinery, but its current projection is not an array-element resolver and has no `long` named-constant path. Reusing the existing expression form for integer array elements is architecturally plausible only if the same-class candidate and ambiguity rules remain explicit and each rewritten element is tied to its bytecode origin; equal values alone are not source-symbol evidence. `Long.MAX_VALUE`/`Long.MIN_VALUE` can be handled as known Java type constants by formatting, but that should remain distinguished from claiming recovery of an input field name.
