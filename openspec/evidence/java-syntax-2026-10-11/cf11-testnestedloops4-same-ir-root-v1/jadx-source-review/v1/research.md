# CF11: JADX loop-exit handling vs. Jarde's current walk

Read-only source review. No JADX/Jarde toolchain was run. JADX source tree: `/Users/lordcasser/workspace/testzone/jadx` (the locally used source checkout; this is source inspection, not a claim that this checkout produced the captured runtime). Jarde trace: `/private/tmp/jarde-cf11-testnestedloops4-diagnostic-root-v2/0.stderr.raw`.

The captured Jarde facts are more specific than the source-level shape: the canonical graph has outer natural loop header BCI 5 and nested natural loop header BCI 17 with blocks `{17,23,56}`. At BCI 23, the inner loop body frame's scope excludes BCI 28 and its successor BCI 31. The BCI-23 conditional therefore produces an empty then arm and no join; the enclosing BCI-17 region returns an `If { join: None }`. The outer BCI-10 conditional later reaches `loop_arm_join_source` and is refused because that helper only accepts a closed loop arm with a proved exit equal to the enclosing join. This is observed from the same-IR trace, not inferred from Javap.

In JADX, `LoopRegionMaker.process` starts from `LoopInfo.getExitNodes`, orders candidate exits, builds a loop region, and uses its condition to decide which blocks are the loop condition and which are body (`LoopRegionMaker.java:61-98, 131-178`). `makeLoopRegion` skips exception-handler exits, non-`IF` exits, and nested-loop conditions; it also checks preconditions and asks `checkLoopExits` to validate multiple exits (`:187-245`). Thus the block that looks like an exit is not enough: it must fit a loop condition and the complete exit shape.

For multiple exits, `checkLoopExits` treats a direct single-instruction return after the proposed header as a valid terminal route (`:264-287`). Otherwise `validOutBlock` examines each loop exit's dominance frontier and accepts only recognized crossings: convergence at the proposed out block, method exit, an edge that validly reaches an outer loop/handler, no work before the end, a constrained nested-if crossing, or an already-labelled outer outblock (`:297-360`, `:368-414`, `:467-524`). Break insertion is edge-specific: `insertLoopBreak` searches from an exit edge toward a crossing and inserts a break only when it can confirm the edge/target relationship (`:652-702`). This is a mutable CFG region-construction algorithm with explicit break/continue edge annotations, not just a natural-loop membership predicate.

`LoopRegionVisitor` runs after region construction and before variable processing (`LoopRegionVisitor.java:45-67`). Its indexed-loop conversion requires a single two-input phi, the increment result as one input, one use of that result, a single-use init, and uses confined to the loop (`:87-143`, `:407-447`). It marks init/increment `DONT_GENERATE` and stores a `ForLoop`. This later pass explains JADX's for syntax; it is not the source of loop exit ownership or a safe recipe for expanding Jarde's scope.

The useful correspondence in Jarde is to keep the natural-loop scope explicit in `Frame` and treat leaving it as the end of that body walk (`region.rs:2162-2187`); prove each branch edge and loop owner from `NormalFlowView`; and distinguish an early terminal return from a break/continue gateway by its actual operation and edge target. Existing `loop_arm_join_source` already requires a loop exit at the enclosing join, closed body regions, and canonical natural-loop ownership (`region.rs:4632-4685`). Those are good places to consult when assessing the outer BCI-10 refusal.

Do not copy JADX's broad “valid out block” exceptions or let a nested loop borrow blocks outside its natural-loop scope merely because the outer loop can reach them. In this class, BCI 28→31 is after the BCI-17 loop's natural latch at 56; admitting it as that inner loop's body would cross into the enclosing loop's continuation and risk assigning ownership to the wrong loop. Also do not infer that BCI 62 is a join merely because several exits reach it: an early return is a terminal path, while an outward edge can represent an outer-loop continuation. Jarde should retain exact edge, frame boundary, and owner checks; any added shape must prove those facts in this real graph and preserve the current refusal where the representation does not yet carry a safe nested-loop continuation.
