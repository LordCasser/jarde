That attribution is source-based inference from the returned region and gate, not a directly logged decision.

In JADX, `LoopRegionMaker.process` starts from `LoopInfo.getExitNodes`, orders candidate exits, builds a loop region, and uses its condition to decide which blocks are the loop condition and which are body (`LoopRegionMaker.java:61-98, 131-178`). `makeLoopRegion` skips exception-handler exits, non-`IF` exits, and nested-loop conditions; it also checks preconditions and asks `checkLoopExits` to validate multiple exits (`:187-245`). Thus the block that looks like an exit is not enough: it must fit a loop condition and the complete exit shape.

For multiple exits, `checkLoopExits` treats a direct single-instruction return after the proposed header as a valid terminal route (`:264-287`). Otherwise `validOutBlock` examines each loop exit's dominance frontier and accepts only recognized crossings: convergence at the proposed out block, method exit, an edge that validly reaches an outer loop/handler, no work before the end, a constrained nested-if crossing, or an already-labelled outer outblock (`:297-360`, `:368-414`, `:467-524`). Break insertion is edge-specific: `insertLoopBreak` searches from an exit edge toward a crossing and inserts a break only when it can confirm the edge/target relationship (`:652-702`). This is a mutable CFG region-construction algorithm with explicit break/continue edge annotations, not just a natural-loop membership predicate.

`LoopRegionVisitor` runs after region construction and before variable processing (`LoopRegionVisitor.java:45-67`). Its indexed-loop conversion requires a single two-input phi, the increment result as one input, one use of that result, a single-use init, and uses confined to the loop (`:87-143`, `:407-447`). It marks init/increment `DONT_GENERATE` and stores a `ForLoop`. This later pass explains JADX's for syntax; it is not the source of loop exit ownership or a safe recipe for expanding Jarde's scope.

The useful correspondence in Jarde is to keep the natural-loop scope explicit in `Frame` and treat leaving it as the end of that body walk (`region.rs:2162-2187`); prove each branch edge and loop owner from `NormalFlowView`; and distinguish an early terminal return from a break/continue gateway by its actual operation and edge target. Existing `loop_arm_join_source` requires a loop exit at the enclosing join, closed body regions, and canonical natural-loop ownership (`region.rs:4632-4685`). These are relevant gates for the outer BCI-10 path, though the diagnostic did not directly report which gate returned `None`.

Do not blindly expand a natural-loop set or copy JADX's mutable CFG rewrites. At the same time, BCI 28→31 is physically before the BCI-17 latch at 56 and belongs to the Java body as a valid side-exit subgraph: after the `k` loop, that path breaks the enclosing `j` loop; it is not inherently outside the Java loop body. The proof challenge is to preserve the natural set `{17,23,56}` while accounting for the side path: show that 23→28 is a single-entry route, that 31 owns its nested loop, and that its exit at 53→62 represents the enclosing `j` break, while BCI 45 is a terminal return. The outer-loop continuation starts at BCI 62. A correct extension must prove those distinct owners and routes without claiming BCI 28 or 31 as members of the inner loop. JADX's multiple-exit/outblock analysis is a useful model for asking these closure questions, but its dominance-frontier exceptions and edge mutation cannot be copied as Jarde proofs. Keep exact edges, frame boundaries, and owner checks; add only the smallest certificate that carries this side-exit ownership safely.
